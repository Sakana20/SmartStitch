# NAS 多机配置编辑锁与无密码用户标识设计

## 1. 背景与目标

SmartStitch 当前由多台电脑分别运行独立的前后端服务，共同读取 NAS 上的配置文件和视频库。这样可以分摊扫描、切片和渲染压力，但不同服务进程之间没有共享内存锁。

当前普通配置保存会把浏览器中的完整配置直接写回 YAML。若两个人基于同一个旧版本同时编辑，后保存者会覆盖先保存者的修改。现有 `threading.RLock` 只能保护单个 Python 进程，不能协调不同电脑；原子替换只能降低文件写坏的概率，也不能避免业务内容被覆盖。

本设计的目标是：

1. 使用无需密码的用户名标识当前操作者。
2. 同一时间只允许一人编辑同一份配置。
3. 其他电脑仍可读取配置、扫描素材和创建渲染任务，不因编辑锁而停止工作。
4. 编辑者异常退出、电脑休眠或断网后，锁可以自动恢复，不形成永久死锁。
5. 即使锁失效或被接管，保存时仍不能静默覆盖别人的新版本。
6. 兼容多台电脑分别运行服务、共享 NAS 的现有部署方式，不引入必须常驻的中心服务器。

本功能用于团队协作和误操作防护，不是安全认证系统。用户名无需密码，因此不能用于权限控制、追责或防止恶意冒用。

## 2. 结论

“一个人进入编辑状态后，其他人看到占用提示”的产品思路合理，适合当前团队规模和 NAS 架构。

不建议把“某某正在打开”直接写进业务 YAML。建议采用：

- NAS 侧独立的配置租约锁；
- 本地保存的无密码用户标识；
- 定时心跳和自动过期；
- 保存和接管共用的短期提交互斥锁；
- 保存时强制校验锁令牌和配置内容哈希；
- 唯一临时文件加原子替换。

其中“锁”负责减少多人同时编辑，“内容哈希校验”负责在极端竞争和异常恢复时阻止最后写入覆盖。两者需要同时存在，不能只做其中一个。

## 3. 为什么不把锁信息写进 YAML 正文

例如不应在配置中增加以下运行时字段：

```yaml
editing:
  username: 张三
  opened_at: 2026-09-18T10:00:00+08:00
```

主要问题如下：

1. **抢锁仍然存在竞争**：两台电脑需要先写 YAML 才能声明自己占用，但“谁能写”正是尚未解决的问题。
2. **打开配置会改变业务版本**：现有 `content_hash` 根据整个 YAML 计算；仅打开编辑器就会改变哈希，影响切片和任务版本校验。
3. **造成无意义备份**：当前每次保存都会备份 YAML，打开、心跳和关闭都会产生大量备份。
4. **异常退出会留下永久状态**：浏览器崩溃或电脑断电时无法把 `editing` 字段清除。
5. **运行时状态污染业务配置**：配置文件应描述素材、时间线和输出规则，不应同时承担在线状态存储。
6. **跨进程临时文件仍可能冲突**：当前固定使用同一个 `.yaml.tmp` 文件，不适合两个服务进程同时写入。

因此，锁信息应放在配置正文之外。

## 4. 用户标识设计

### 4.1 首次使用

用户首次打开 SmartStitch 时输入一个显示名称，例如“张三”。不要求密码。

建议同时生成以下标识：

- `user_id`：随机 UUID，持久保存在当前电脑，用于区分同名用户。
- `display_name`：用户输入的中文名称，用于界面展示。
- `device_name`：电脑名称，例如“剪辑室-Mac-02”。
- `service_instance_id`：当前电脑上的 SmartStitch 服务实例 UUID，保存在本机 `data/`，重启后保持不变。
- `browser_session_id`：当前标签页的随机 UUID，保存在 `sessionStorage`，关闭标签页后失效。

只比较用户名不足以识别锁的真正持有者。例如两个人都填写“小王”，或同一个人在两台电脑登录，都必须依靠 UUID 和设备名称区分。

### 4.2 登录信息保存位置

登录信息不写入业务 YAML，也不建立 NAS 用户数据库。建议明确分为以下三层：

#### 本机用户资料

每台电脑把当前用户保存到 SmartStitch 本机数据目录：

```text
<SmartStitch 本机目录>/data/user-profile.json
```

示例：

```json
{
  "schema_version": 1,
  "user_id": "f93c5e24-7f21-4e24-8898-01b8295e5d4e",
  "display_name": "张三",
  "created_at": "2026-09-18T09:30:00+08:00",
  "updated_at": "2026-09-18T09:30:00+08:00"
}
```

该文件由本机后端读写，对应 `GET/PUT /api/v1/users/me`。关闭浏览器或重启 SmartStitch 后用户名仍然保留。修改显示名称保留原 `user_id`；若一台电脑换人使用，应通过“切换用户”生成新的 `user_id`，避免把两个人识别为同一人。

#### 本机服务实例

电脑和服务实例信息保存在：

```text
<SmartStitch 本机目录>/data/service-instance.json
```

示例：

```json
{
  "schema_version": 1,
  "service_instance_id": "6b5a7f7f-606f-4dde-a75c-6354645204b7",
  "device_name": "剪辑室-Mac-02"
}
```

`service_instance_id` 首次启动时生成，后续重启保持不变。`device_name` 默认读取系统电脑名称，也允许用户设置更容易识别的名称。

#### 浏览器标签页会话

每个标签页把 `browser_session_id` 保存到浏览器 `sessionStorage`，建议键名为 `smartstitch.browser_session_id`。同一电脑打开两个标签页时，它们属于不同编辑会话；关闭标签页后该 ID 自动失效。

#### NAS 共享信息

只有用户取得某个配置的编辑锁时，才把当前用户、设备和会话的副本写入 NAS：

```text
/Volumes/home/Smartstitch/.smartstitch-locks/<config-id>.edit.lock/owner.json
```

这个文件只是当前占用快照，用于让其他电脑显示“张三正在剪辑室-Mac-02编辑”。正常释放锁后随锁目录一起移除；它不是长期用户资料。业务 YAML 中不保存任何登录或在线状态。

因此，数据归属为：

| 数据 | 保存位置 | 生命周期 |
|---|---|---|
| 用户名、`user_id` | 本机 `data/user-profile.json` | 持久保存，直到切换用户 |
| 电脑名、服务实例 ID | 本机 `data/service-instance.json` | 持久保存，直到重置本机实例 |
| 标签页会话 ID | 浏览器 `sessionStorage` | 当前标签页生命周期 |
| 当前配置占用者 | NAS 锁目录中的 `owner.json` | 当前编辑租约生命周期 |

### 4.3 身份边界

无密码用户系统只提供以下能力：

- 在锁提示中显示是谁、在哪台电脑上编辑；
- 记录锁获取、续租、释放和接管信息；
- 避免其他浏览器误释放当前持有者的锁。

它不提供登录安全性。任何能访问系统的人仍可以修改自己的显示名称，也可能通过接口伪造身份。若未来需要权限、审计或管理员角色，应升级为真正的账号认证系统。

## 5. 锁的范围

锁按配置 ID 隔离。一份配置一个锁，不同配置可以由不同用户同时编辑。

### 5.1 不需要锁的操作

- 在配置下拉框中选择并查看配置；
- 扫描素材；
- 预览组合；
- 创建渲染任务；
- 执行已经创建的渲染任务；
- 查看任务、日志和历史结果。

渲染任务创建时已有配置快照，任务开始后不应长期持有编辑锁。

### 5.2 必须持锁的操作

- 打开简单模式、高级模式或 YAML 专家模式进行编辑；
- 保存配置；
- 修改并保存素材权重、标签和启用状态；
- 新增、修改、排序或删除视频库、利益点；
- 更换风险提示语图片；
- 删除配置；
- 其他任何会写入该配置 YAML 的接口。

配置克隆只读取源配置，但需要对新配置 ID 做独占创建；不需要锁住源配置。自动迁移不应在普通读取过程中静默改写 YAML，应改为显式迁移，或先获取短期系统写锁。

### 5.3 何时视为“打开”

不建议用户只是在下拉框中选中配置就加锁，否则一个人进行渲染会阻止其他人编辑，失去多机分摊性能的意义。

建议把“打开”定义为进入明确的编辑状态：

- 点击“编辑配置”时获取锁；
- 权重页面增加“编辑权重”状态，进入时获取同一把锁；
- 删除配置等单次写操作在执行前获取短期锁。

## 6. NAS 侧锁文件结构

建议在共享配置目录中增加隐藏目录，不修改原 YAML：

```text
/Volumes/home/Smartstitch/
├── taobao-xingguang-erjian.yaml
├── backups/
└── .smartstitch-locks/
    ├── taobao-xingguang-erjian.edit.lock/
    │   ├── owner.json
    │   └── heartbeat
    └── taobao-xingguang-erjian.commit.lock/  # 仅在保存或接管期间短暂存在
```

`owner.json` 示例：

```json
{
  "schema_version": 1,
  "config_id": "taobao-xingguang-erjian",
  "display_name": "张三",
  "user_id": "f93c5e24-7f21-4e24-8898-01b8295e5d4e",
  "device_name": "剪辑室-Mac-02",
  "service_instance_id": "6b5a7f7f-606f-4dde-a75c-6354645204b7",
  "browser_session_id": "bd786ea2-0e55-4db9-86ca-c648d3e36e5c",
  "lease_token": "随机且不可猜测的令牌",
  "acquired_at": "2026-09-18T10:00:00+08:00",
  "last_heartbeat_at": "2026-09-18T10:00:30+08:00",
  "lease_seconds": 120,
  "base_config_hash": "打开编辑器后重新读取到的 SHA-256"
}
```

`lease_token` 不承担用户认证，但可以避免另一个标签页或普通释放请求误删不属于自己的锁。

## 7. 锁获取与租约算法

### 7.1 获取锁

1. 后端尝试原子创建 `<config_id>.edit.lock` 目录。
2. 目录创建成功的请求是唯一获胜者。
3. 获胜者使用唯一临时文件写入 `owner.json`，再原子替换目标文件。
4. 获取成功后重新读取一次 YAML 和 `content_hash`，前端必须以这个最新版本建立编辑草稿。
5. 若锁目录已经存在，读取持有者和心跳状态：
   - 租约仍有效：返回 `423 Locked`；
   - 租约已过期：执行安全接管流程后再次竞争锁。

使用目录创建作为竞争点，是因为同一 NAS 目录下的原子 `mkdir` 通常比长期依赖 `flock`/`fcntl` 更容易跨 macOS、Windows、SMB 和 NFS 工作。但必须在实际 NAS 协议上做并发验证，不能只依赖本机测试。

### 7.2 心跳

- 前端持有编辑器期间，每 15 秒请求一次续租。
- 建议租约有效期为 120 秒，允许浏览器后台计时器延迟和短暂网络抖动。
- 续租时后端必须核对 `lease_token`、配置 ID和会话 ID。
- 心跳应使用唯一临时文件加原子替换，或安全更新独立 `heartbeat` 文件。
- 页面隐藏时继续心跳；电脑睡眠或网络断开超过租约后，锁自动过期。

关闭页面时可以通过正常接口或 `sendBeacon` 尝试释放，但不能依赖 `beforeunload` 一定执行，自动过期才是最终保障。

### 7.3 正常释放

以下动作释放锁：

- “保存并关闭”成功完成；
- 用户确认放弃未保存内容并关闭；
- 切换到其他配置并确认放弃当前草稿；
- 显式点击“退出编辑”。

释放时必须核对 `lease_token`。普通用户不能释放另一个会话仍然有效的锁。

### 7.4 过期与接管

过期锁不直接覆盖。接管者先获得同一配置的短期提交互斥锁，再把旧编辑锁目录原子重命名为带 UUID 的 `.stale` 记录，最后重新执行 `mkdir` 竞争。多台电脑同时发现过期锁时，仍只能有一台成功创建新锁。

界面可以提供：

- 活跃锁：仅显示“由张三在剪辑室-Mac-02编辑，请联系同事保存并关闭”。
- 已过期锁：显示“上次心跳已超过 2 分钟”，允许点击“接管编辑”。
- 立即强制接管活跃锁：V1 不建议提供。无密码系统无法可靠判断谁是管理员，容易把正常编辑者踢掉。

### 7.5 短期提交互斥锁

编辑租约持续数分钟，提交互斥锁只覆盖一次很短的文件事务。保存配置、释放编辑锁和接管过期锁都必须先竞争 `<config_id>.commit.lock`，获得者才能继续。

它解决以下竞态：旧编辑者刚校验完租约时进程暂停，另一个用户接管并保存，旧进程恢复后又覆盖新内容。提交锁内必须完成“复查编辑租约 → 复查内容哈希 → 写临时文件 → 替换 YAML”的完整流程；锁接管也必须等待当前提交结束。

提交锁同样需要唯一持有令牌和异常恢复信息，但超时时间可以更短，例如 60 秒。若提交锁过期，接管前仍应检查临时文件和最终 YAML 状态并记录诊断，不能直接假定上一笔写入从未发生。

## 8. 保存时的双重校验

只有编辑锁仍然有效还不够。第一版通过统一请求头让所有配置写接口同时接收租约和版本：

```http
X-SmartStitch-Lease: <lease_token>
X-SmartStitch-Config-Hash: <打开编辑器时读取到的 SHA-256>
```

业务请求体继续保存配置或具体操作参数；锁续租和释放接口则在请求体中提交 `lease_token` 与 `browser_session_id`。

后端先获取该配置的短期提交互斥锁，并在同一个写入临界区依次检查：

1. 当前锁属于该 `lease_token`；
2. 租约没有过期；
3. NAS 上配置的当前哈希等于 `expected_config_hash`；
4. 新配置通过模型校验；
5. 使用唯一临时文件写入，例如 `.<config-id>.<uuid>.tmp`；
6. 原子替换 YAML，并生成备份；
7. 返回新的 `content_hash`，更新编辑锁中的 `base_config_hash`；
8. 释放短期提交互斥锁。

任一条件不成立都不得写入：

- 锁不属于当前用户或已经过期：返回 `423 Locked`；
- 配置内容已变化：返回 `409 Conflict`；
- 配置格式错误：返回 `422 Unprocessable Entity`。

这样即使某台电脑在编辑过程中休眠、锁过期并被别人接管，旧页面醒来后也不能把新内容覆盖掉。

## 9. 推荐接口

```text
GET    /api/v1/users/me
PUT    /api/v1/users/me

GET    /api/v1/configs/{config_id}/lock
POST   /api/v1/configs/{config_id}/lock/acquire
POST   /api/v1/configs/{config_id}/lock/renew
DELETE /api/v1/configs/{config_id}/lock
POST   /api/v1/configs/{config_id}/lock/takeover
```

建议锁冲突响应：

```json
{
  "detail": {
    "code": "config_locked",
    "message": "张三已打开此配置，请先联系同事保存关闭",
    "owner": {
      "display_name": "张三",
      "device_name": "剪辑室-Mac-02"
    },
    "acquired_at": "2026-09-18T10:00:00+08:00",
    "last_heartbeat_at": "2026-09-18T10:01:15+08:00",
    "stale": false
  }
}
```

所有会写 YAML 的现有接口都需要增加统一的锁校验，不能只保护“保存配置”按钮。推荐在后端集中实现 `assert_write_lease()` 和统一的提交临界区，避免新增接口时遗漏。
## 10. 前端交互

### 10.1 用户名

- 首次进入时显示简短弹窗：“请输入你的名字，方便同事识别谁正在编辑。”
- 页面右上角持续显示当前用户名和电脑名称，并允许修改显示名称。
- 用户名为空时可以查看和渲染，但不能进入任何配置写入状态。

### 10.2 成功获得锁

- 打开最新配置内容，而不是使用页面上可能已缓存的旧草稿。
- 编辑器顶部显示：“你正在编辑 · 张三 · 自动保持占用”。
- 心跳失败一次先提示网络不稳定；连续失败接近租约期限时禁用保存，并明确提示先恢复 NAS 连接。

### 10.3 被别人占用

点击“编辑配置”后显示阻断弹窗：

> 张三正在“剪辑室-Mac-02”编辑此配置。  
> 打开时间：10:00，最近在线：10:01。  
> 请联系同事保存并关闭后再试。

提供“重新检测”按钮。可以提供“只读查看”，但所有输入框和写操作必须禁用，且只读页面不能复用可提交的编辑草稿。

### 10.4 关闭与未保存内容

- 有未保存内容时，关闭按钮先询问“放弃修改并释放配置吗？”
- “保存并关闭”必须先保存成功，再释放锁。
- 保存失败时不得自动释放锁，以免用户无法重试。
- 释放失败时提示锁将在约 2 分钟后自动过期。

## 11. NAS 与时间相关风险

### 11.1 NAS 原子语义

不同 NAS、SMB/NFS 版本和缓存策略对 `mkdir`、`rename`、目录可见性可能存在差异。上线前必须在实际两台电脑上验证：

- 同时抢锁只能有一个成功；
- 获胜者写入的 owner 信息能被另一台及时读取；
- 心跳在合理时间内可见；
- 断网、休眠和服务退出后能按预期过期；
- 原子替换不会产生空文件或半份 YAML。

### 11.2 时钟偏差

租约判断依赖时间。所有电脑和 NAS 应开启自动时间同步。建议用较宽松的 120 秒租约，并同时记录 ISO 时间和 heartbeat 文件修改时间。若检测到明显的未来时间或时钟偏差，禁止自动接管并提示人工检查。

### 11.3 NAS 暂时不可用

NAS 不可访问时不得把“读取不到锁”当成“没有锁”。正确行为是禁止进入编辑状态，保留只读页面，并提示检查共享目录连接。

## 12. 与集中式锁服务的比较

### 方案 A：NAS 租约锁（推荐当前采用）

优点：

- 不需要额外常驻服务器；
- 符合当前每台电脑独立运行 SmartStitch 的方式；
- NAS 可用时所有实例都能看到同一状态；
- 实现和运维成本较低。

缺点：

- 可靠性依赖实际 SMB/NFS 行为；
- 需要心跳、过期和异常接管逻辑；
- 无密码身份不能提供真正权限。
- 在 NAS 不提供可靠原子目录操作的情况下，无法达到严格的分布式一致性。

### 方案 B：单独的中心协调服务

优点：

- 锁、在线状态和审计更容易保证一致性；
- 以后可以扩展消息提醒、管理员和权限系统。

缺点：

- 中心服务成为新的部署依赖和单点故障；
- 与当前纯本地服务结构相比明显更复杂。

当前规模下先采用方案 A 是合理的，但接口和锁数据模型应保持独立，未来可以把锁存储从 NAS 替换为中心服务，而不重做前端交互。

## 14. 测试与验收

至少覆盖以下场景：

1. 两台电脑同时获取同一配置锁，恰好一台成功。
2. 两台电脑分别编辑不同配置，都能成功。
3. A 持锁时，B 收到包含 A 姓名和设备的占用提示。
4. A 正常保存并关闭后，B 可以立即获取。
5. A 浏览器崩溃、服务退出、电脑断网或休眠后，B 可以在租约过期后接管。
6. A 的旧页面在锁被 B 接管后恢复，保存必须失败，不能覆盖 B 的内容。
7. 持锁期间配置被人工直接修改，保存返回 `409`。
8. NAS 断开时不能错误地认为锁不存在。
9. 渲染任务在别人编辑配置时仍可依据已有快照正常运行。
10. 并发写入不会产生空 YAML、半份 YAML或遗留的共用 `.yaml.tmp`。
11. 同名用户、同一用户多标签页和同一用户多设备都能被正确区分。
12. 心跳被浏览器节流时不会频繁误判过期。

## 15. 建议先确认的产品决策

在开发前建议确认以下三点：

1. **锁的入口**：是否同意只在“进入编辑状态”时加锁，而不是选中配置或渲染时加锁。本文建议前者。
2. **过期时间**：是否接受 15 秒心跳、120 秒自动过期。时间更短恢复更快，但更容易因网络抖动误释放。
3. **强制接管**：V1 是否只允许接管已过期锁，不允许立即抢占仍活跃的锁。本文建议如此。

若以上决策确认，NAS 租约锁加保存时哈希校验可以较低成本解决当前多人覆盖问题，并继续保留多机并行切片和渲染的优势。

## 16. 当前实现状态

第一版已经落地以下能力：

- 本机 `data/user-profile.json` 用户资料与 `data/service-instance.json` 服务实例；
- 首次打开时设置无密码用户名，顶部可查看或切换用户；
- NAS `.smartstitch-locks/` 编辑租约和短期提交锁；
- 配置锁获取、查询、15 秒心跳、释放和过期接管接口；
- 打开配置编辑器前先获取租约，被占用时显示同事姓名和电脑名称；
- 配置保存、YAML 保存、视频库/利益点变更、风险图、权重和删除配置的租约校验；
- 所有配置写入同时校验 `content_hash`，旧页面不能覆盖新版本；
- 配置临时文件改为 UUID 唯一文件，避免不同服务共用 `.yaml.tmp`；
- 正常关闭主动释放，异常关闭由 120 秒租约兜底；
- 双服务实例竞争、错误令牌、旧哈希、正常释放和过期接管的自动化测试。

素材权重页进入时获取与配置管理相同的配置级独占编辑租约并持续续租，离开页面时释放。权重、标签和启用状态只形成页面草稿，不自动保存；用户点击“保存权重”时使用当前已持有的租约和进入页面时的配置版本统一提交。无法取得租约时页面只读；存在未保存修改时离开页面必须确认是否放弃。该方案既阻止多人同时编辑，也避免在保存瞬间临时抢锁造成交互含义不清。

代码级回归已经通过；正式投入多人使用前，仍需在实际 NAS 和两台真实电脑上执行第 14 节的并发、断网、休眠和缓存可见性验收。实际 NAS 双机测试是本功能上线前的必要条件。
