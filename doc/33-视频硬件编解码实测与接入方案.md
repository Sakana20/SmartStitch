# 视频硬件编解码实测结论与分阶段接入方案

测试日期：2026-09-29。环境：macOS 26.6.2、arm64，系统 FFmpeg 7.1 系列；VFR 使用项目虚拟环境 PyAV 16.1.0 自带的 FFmpeg 库。系统 FFmpeg 版本为 7.1；PyAV 库版本为 libavcodec 62.11.100、libavformat 62.3.100。

状态：已完成有限样片实测，并接入第一、第二阶段的硬件优先及独立回退。设置页“软解编解码”开关已实现持久化与新任务快照；切片硬解、ProRes Alpha 硬编和超分硬编等后续阶段尚未切换。

## 方法与范围

- 首次可行性实测时未修改业务代码或默认编码策略；独立测试脚本调用命令构造器，或在内存中编译仅替换编解码参数的超分函数副本。后续实施状态见下文。
- 真实运行 FFmpeg、PyAV 和已有 x2plus / animevideo CoreML 模型，没有模拟模型推理。
- 编码设置 `allow_sw=0`，禁止 VideoToolbox 编码器内部软件回退。解码通过 debug 日志中的 `Format videotoolbox_vld chosen by get_format()` 确认；H.264 另做强制硬件帧及 hwdownload 检查。
- 沙箱内创建 VideoToolbox 会话报 -12908；经过自动审批，硬件测试在沙箱外运行成功。这种环境错误不能用于判断本机不支持硬编。
- 横竖转换使用 720p 输入，输出分别为 720p / 1080p；超分模型测试使用 96×160 短样片。素材由 FFmpeg 生成，包含运动图案、分数帧率、有声音轨、VFR、透明和半透明图案。
- 集群仅测试同一台机器上的实际分段编码、无损拼接、最终合音频和校验，没有进行第二台 Mac / NAS 网络调度测试。
- 音频继续使用现有软件 AAC 路径，只核对音轨保留；本次是视频硬件编解码测试。

## 功能结果

| 功能 | 结果 | 核对内容 |
|---|---|---|
| A+B 文件夹拼接 | 硬解硬编通过 | 两个输入确认为硬解；软硬输出尺寸、118 帧、音轨及时间戳一致 |
| 横改竖 / 竖改横 | 720p / 1080p 硬解硬编通过 | 59 帧、分数帧率时间戳、尺寸、音轨与软件基线一致 |
| VFR 横竖转换 | 通过 | 45 帧、逐帧 PTS 与软件输出一致 |
| 普通 / 组合切片 | 硬解硬编通过 | 非关键帧附近的时间裁切及不连续帧区间组合；24 / 21 帧，时间戳、音轨一致；同步与后台入口共用这些底层命令 |
| H.264 视频特效叠加 | 硬解硬编通过 | 主视频、循环特效视频都确认硬解；58 帧输出与软件基线一致 |
| QTRLE 透明特效 | 软解 + 硬编通过，强制硬解失败 | QTRLE 没有输出硬件帧；仅添加 hwaccel 参数会继续软解，不能误报为全部硬解 |
| 黑底转 ProRes 4444 Alpha | 硬解硬编通过 | 日志明确为 appleproreshw.4444；30 帧透明 / 半透明 Alpha 与软件版最大差 1/255，平均差约 0.049/255 |
| ProRes 4444 Alpha 解码 | 硬解通过 | 确认硬件帧路径；透明 / 不透明区域保持，灰色半透明样片缩小抽样与软件解码最大差 1/255 |
| CFR 超分，两种模型 | 真实模型 + 硬解硬编通过 | 12 帧、原尺寸、最终音轨；软件基线与硬件输出帧数、PTS 一致 |
| VFR 超分，两种模型 | 真实模型 + 硬解硬编通过 | 9 帧；通过项目 verify_vfr_video 的 PTS、末帧时长、音轨和起点校验 |
| CFR / VFR 超分分段拼接 | 通过 | x2plus 分为两段真实处理，视频 copy 拼接后恢复音频；VFR 最终通过项目逐帧时间戳校验 |
| 场景分析 | 硬解通过 | 红转蓝测试在软硬路径均检出 1 秒处切点；只是有限样片一致性验证 |
| 透明通道抽样检查 | ProRes 硬解通过 | 透明分类一致；64×64 样本最大差 1，逐字节相等条件不成立 |
| VFR 时间戳扫描 | FFmpeg 硬解原型通过 | 45 帧 PTS 完全一致；使用 showinfo 原型，当前业务 ffprobe 扫描函数未改动 |

## 性能与画质

10 秒样片，三轮交替软硬执行，以下为包含进程启动、滤镜、视频和音频编码的端到端耗时中位数：

| 流程 | 软件 | 硬件 | 结果 |
|---|---:|---:|---|
| 普通精确切片，720p | 0.874 秒 | 0.874 秒 | 本样片无明显收益 |
| 竖改横，720p | 3.233 秒 | 2.852 秒 | 耗时减少约 11.8% |

透明抽样软件 0.099 秒、硬件 0.252 秒；45 帧时间戳扫描软件 0.049 秒、硬件 0.145 秒。它们是单轮小任务，硬件初始化开销明显，不支持直接改成默认硬解的结论。

软件 CRF 18 与硬件质量 65 的输出 SSIM 比较：拼接 0.996907，横改竖 0.996606，普通切片 0.996998，视频特效 0.996115；超分短小样片 x2plus 0.982096、animevideo 0.983833。该指标衡量两种编码结果的差异，不是相对于无损参考的质量评分，也不等于主观画质合格。超分正式替换前应比较更高硬件质量参数和真实 720p / 1080p 素材。

## 接入判断

1. 拼接、横竖转换、普通 / 组合切片与 H.264 视频特效，已有可运行的硬解硬编依据；性能收益仍须按真实素材判断。
2. 本机 ProRes 4444 Alpha 可以硬编，此前只能软件编码的推断过于保守；接入时应独立探测 ProRes 硬编能力，使用支持 Alpha 的输入像素格式，并保留软件回退。
3. QTRLE 应保留软件解码。硬解、硬编需要分别记录，不能将编码成功等同于全部硬件处理。
4. 两种超分模型、CFR / VFR 和分段拼接均已证明技术上可行；此次没有覆盖跨设备编码参数一致性、真实长片、复杂非零起点或并发资源争用。
5. 场景 / 透明 / 时间戳分析只证明有限样片兼容，尚不支持全量默认硬解；音频未做硬件加速测试。


## 首次审计时的软件路径与原因

| 模块 | 实施前的实现 | 原因与改动边界 |
|---|---|---|
| `jobs.py` / `renderer.py` | 文件夹拼接在 `_folder_concat_config()` 写死 libx264；主成片默认 VideoToolbox，失败整体软解软编 | 文件夹入口未接统一硬件策略；渲染器把解码与编码绑定回退 |
| `landscape_to_portrait.py` / `portrait_to_landscape.py` | 共用模糊背景管线，优先硬编，未启用硬解 | 编码器选择已接入，解码尚未接入；CPU 滤镜不是强制软解的理由 |
| `slicer.py` / `slice_jobs.py` | 后台切片优先硬编；旧同步入口使用软件策略；两者输入均软解 | 新旧入口策略不同，底层普通与组合切片可共用独立解码策略 |
| `renderer.py` 附加输入 | 主时间线启用硬解，循环特效与视频边框未启用 | 应逐输入选择；QTRLE 保持软解，H.264、ProRes Alpha 按能力尝试 |
| `video_upscale.py` / `vfr.py` | CFR FFmpeg、VFR PyAV 固定 libx264，FFmpeg 解码后输出 RGB | 首版画质优先；VFR 要精确保留 PTS 和帧时长；模型需要 CPU 可访问的 RGB 数据，但不强制使用软件解码 |
| `cluster_upscale.py` / `cluster.py` | 各分段统一软件编码后 copy 拼接 | 节点输出必须满足同一编码协议，不能各自无约束地切换编码器 |
| `prores_alpha.py` | prores_ks，RGBA / geq 生成 Alpha | 输出格式与 Alpha 需求不同于 H.264；本机已验证独立的 ProRes 硬编路径 |
| `timeline.py` / `scanner.py` / 超分探测 | 场景、透明、完整帧时间戳分析使用软件处理 | 分析结果一致性与短任务初始化开销须单独验证；ffprobe 不能仅靠照搬 FFmpeg 输入参数改成已验证的硬解实现 |

上述原因中，首版画质和集群一致性有设计依据；其余“尚未接入”的判断来自当前命令构造和入口策略，不能当作无法硬件加速的格式限制。

## 横竖转换的模糊滤镜方案

处理顺序固定为：

```text
VideoToolbox 硬解
  → 将帧交给 CPU 滤镜
  → 按旋转和像素比例统一显示方向
  → split：背景缩放 / 裁切 / gblur；前景等比缩放
  → overlay 合成，format=yuv420p
  → VideoToolbox H.264 硬编
```

本轮直接复用了现有 split、scale、crop、gblur、overlay 滤镜图，只增加硬解并选择硬编，不修改模糊效果、前景尺寸、位置或时间戳策略。FFmpeg 自动完成本轮格式下的硬件帧到软件帧交接；若后续显式设置硬件输出帧格式，则需同时正确安排 hwdownload 和像素格式转换，不能直接将硬件帧喂给普通 CPU 滤镜。

该方案是硬件解码、CPU 滤镜、硬件编码，并非整条视频处理都在 GPU 上完成。模糊、缩放和帧传输仍有开销，所以仅凭硬件参数不能承诺大幅提速。横改竖、竖改横及其集群整文件任务复用相同管线，保留 `-fps_mode passthrough`、旋转 / SAR 处理和第一音轨映射。

## 实现方案

### 1. 共用能力探测和策略

以 [video_encoding.py](../smartstitch/video_encoding.py) 为基础，整合 renderer 内重复的能力探测，分别提供解码和编码计划，避免 `selected_video_codec == h264_videotoolbox` 决定是否硬解。

- 区分 H.264 硬编、ProRes 4444 硬编和按源视频 codec / profile / pixel format 判断的硬解能力；FFmpeg 列出编码器仅代表可尝试，不等于硬件会话可创建。
- 能力缓存关联 FFmpeg 可执行文件及版本、架构和会话探测结果，更新 FFmpeg 后失效；PyAV 自带 FFmpeg 与系统 FFmpeg 单独探测，不共用编码器存在性结果。
- 本轮仅确认当前 Apple Silicon 环境。其他设备继续使用已验证策略；ProRes 硬编尤其不能仅凭 arm64 标志判定可用。
- H.264 硬编起点沿用质量 65、High profile、yuv420p，启用 `-allow_sw 0`；超分须另行标定质量。软件保留原 preset / CRF，不因回退改变功能规格。
- ProRes 优先尝试 `prores_videotoolbox`、profile 4、支持 Alpha 的输入格式；本轮成功输入为 bgra。不能照搬 prores_ks 的 `-qscale:v 64` 或 H.264 质量配置。
- QTRLE 保持软解；H.264、ProRes 等按已验证的格式探测并尝试。图片、音频和分析任务不直接套用视频硬解策略。

### 2. 解码、编码独立回退

一般视频渲染按有界尝试执行：

```text
硬解 + 硬编
  ├─ 解码失败 → 软解 + 硬编
  ├─ 编码失败 → 硬解 + 软编（硬解仍适用时）
  └─ 无法可靠区分故障阶段 → 软解 + 硬编 → 软解 + 软编
```

已经确定格式不支持硬解时直接软解；已经确定硬编会话不可用时跳过硬编。按有效配置去重尝试，禁止无限重试。硬解格式失败只影响相应输入或当前条目，不应因一个 QTRLE 输入而全局关闭硬解。

每次重试清理临时输出、重置当前尝试进度，复用同一输入快照、输出预留名和已选素材。取消、应用退出、源文件变化、输入损坏及明确的磁盘 / 权限错误不触发编解码兜底。输出在通过现有校验后发布，保留幂等、取消和历史任务行为。

对多输入图层单独建立输入计划，允许主素材硬解、QTRLE 特效软解和输出硬编同时存在。编码会话失败可在当前批次降级；不支持的解码格式不传播为所有素材的失败。

### 3. 任务记录与展示

兼容已有 `planned_video_encoder`、`actual_video_encoder`、`encoder_attempts` 和 `encoder_fallback_reason`，增加以下设计字段：

| 字段 | 含义 |
|---|---|
| `video_decode_inputs` | 每个视频输入的标识、源格式、计划 accelerator、实际确认状态和回退原因 |
| `video_decode_status` | 汇总为 software、hardware_confirmed、mixed、requested_unconfirmed 或 unknown |
| `decoder_fallback_reason` | 解码降级原因摘要 |
| `codec_attempts` | 每次解码 / 编码组合、起止时间、阶段和结果 |
| `encoding_profile` | 输出编码器、像素格式、质量参数；集群还包含协议要求 |

`-hwaccel videotoolbox` 只证明请求硬解，不能直接写成实际硬解成功。可在诊断模式捕获有界 debug 日志确认硬件帧选择；普通运行没有确认信息时显示“已请求硬解 / 未确认”，不要伪造结果。编码强制 `allow_sw=0` 成功后可记录硬编成功。多输入必须允许“混合解码”。

`hardware_acceleration_used` 等旧汇总字段须保留兼容语义，详情分别展示解码与编码，旧记录缺少解码证据时显示未知。正常界面展示实际路径和必要回退原因，不展示长日志或内部测试细节。

### 4. 分阶段接入

| 阶段 | 改动 | 默认策略与放行条件 |
|---|---|---|
| 第一阶段 | 统一策略和独立回退；移除文件夹拼接固定 libx264；补齐普通 H.264 视频特效输入硬解 | 硬件优先，软件兜底；发布前验证真实素材质量和原有任务行为 |
| 第二阶段 | 横竖转换增加硬解，共用本地 / 集群整文件管线 | 保持模糊滤镜和现有硬编；硬解失败单独退软解 |
| 第三阶段 | 普通 / 组合切片增加可选择的硬解；同步旧入口保持兼容 | 先保留现有默认；真实长片和并发吞吐量 / CPU 占用比较通过后决定默认开启，或在迁移后台队列后停用旧接口 |
| 第四阶段 | ProRes Alpha 独立能力探测和硬件策略 | 设备支持时可尝试；本轮无速度优势，默认切换取决于实际素材收益和 Alpha / 色彩验收 |
| 第五阶段 | 本地 CFR / VFR 超分接硬件策略，随后扩展集群 | 先标定画质、验证长片和跨节点一致性，再切默认；模型、原尺寸和时间戳规则不变 |
| 暂缓 | 场景 / 透明 / 时间戳分析，QTRLE 解码 | 保持软件默认；分析需更多一致性与端到端收益证据；QTRLE 本轮强制硬解不通过 |

当前已接入第一、第二阶段及软件偏好开关；其余阶段继续按上述验收条件推进。

### 5. 超分及集群的额外约束

- CFR 沿用 RGB rawvideo 流式管道，仅替换解码和输出编码策略；硬解后的帧仍可用于现有 NumPy / CoreML 输入处理。模型推理可能是主要瓶颈，不能把编解码收益当作超分整体收益。
- VFR 沿用 PyAV 逐帧 PTS / time_base 和 packet duration 写入、bf=0、末帧时长及音视频起点恢复；硬件质量参数要通过 PyAV 自带库单独验证。
- 正式验收覆盖非零起点、有声 / 无声、分数帧率、末帧时长及取消；当前 9 帧零起点测试只验证基本可行性。
- 超分集群为整条源视频先确定统一 encoding_profile，再把同一参数与协议能力要求发给节点；节点要确认所用 FFmpeg / PyAV 管线支持该 profile，主控核对分段流结构、尺寸、time base、像素格式及拼接相关参数。
- 某节点硬编失败优先派给能满足相同 profile 的节点，不能将该段悄悄软编并与硬编段混拼。若需整体软件降级，须丢弃或隔离旧 profile 的分段，按统一软件 profile 重跑整个源视频。
- 保持关键帧可独立解码、CFR / VFR 分段边界、concat duration、最终 copy 拼接和合音频校验。跨节点正式验收完成前不宣称集群硬编方案已上线。

## 后续验收要求

1. 有限能力的策略 / 故障测试：硬解失败但硬编可用、硬编失败但硬解可用、混合格式、多次尝试去重、取消不回退、临时文件清理、输出预留和任务记录兼容。
2. 实际硬件媒体验收：720p / 1080p，H.264、需要支持的其他视频格式、旋转、SAR、CFR / VFR、有声 / 无声，核对帧数、尺寸、逐帧 PTS、时长、末帧时长和音视频起点；硬编不得静默软件回退。
3. 画质验收：相同滤镜和模型输出分别编码，与无损参考比较质量并抽看运动 / 细节；记录输出大小及明确的项目验收阈值。现有软硬输出间 SSIM 不能代替该步骤。
4. Alpha 验收：黑、白、灰、渐变和复杂边缘逐帧核对 Alpha、RGB 与叠加效果，检查透明背景和半透明区域；不将本轮最大 1/255 自动设为所有素材的通过标准。
5. 性能验收：真实长视频、重复运行和并发任务，记录端到端耗时、CPU、内存与吞吐量；硬件路径没有收益的功能可以继续软件默认。
6. 两台真实 Mac 的集群验收：统一 profile，CFR / VFR 分段合并，节点硬编不可用、节点版本不同、网络重试及整片软件降级，不混用未验证的编码结果。

## 2026-09-29 首批实施记录

### 设置开关

设置页原占位开关改为“软解编解码”，删除另一条无功能的设置占位。开关默认关闭：适用的 H.264 输出优先 VideoToolbox；开启后强制软件解码与 libx264 编码，不启动硬件能力探测。偏好保存在本机 data/codec_settings.json，通过 GET / PUT `/api/v1/settings/codecs` 读取和保存，复用现有登录与请求来源校验。

新建成片、文件夹拼接和批量去重任务将偏好写入配置快照，H.264 输出在关闭开关时统一为 h264_videotoolbox，在开启时统一为 libx264；其他自定义编码器关闭开关时保留原配置。横竖转换在创建批次时保存 software_codec_enabled 和 hardware_decode_preferred。排队、预约和运行中的既有任务继续使用创建时的快照，设置变化不改写其策略。后台切片也遵守强制软件偏好，但当前阶段没有新增切片硬解；Alpha、超分和分析路径继续使用原有软件处理。

### 硬件优先与回退

- renderer 的编码器和解码能力改为分别探测；能力列表按 FFmpeg 实际路径、修改时间、大小及运行器缓存，二进制变化后重新读取。
- 文件夹拼接不再写死 libx264；主成片、批量去重及文件夹拼接共用独立回退。
- 主素材、循环视频特效和视频边框逐输入判断格式，本阶段 H.264 / ProRes 可请求 VideoToolbox 解码，QTRLE、其他未确认格式和图片保持软件路径。
- 横竖转换复用现有 CPU 模糊滤镜图，增加符合条件的硬解请求，保留硬编质量、声音和 passthrough 时间戳策略。
- 编码明确禁止内部软件回退。解码失败优先软解 + 硬编；明确的硬编失败优先硬解 + 软编；无法区分时先软解 + 硬编，再软解 + 软编。同一组合只尝试一次，失败临时输出在重试前清理。
- 取消、源文件变化、明确的缺失 / 损坏输入、磁盘空间、权限和 I/O 错误不触发编解码重试。最终输出仍由已有校验和发布逻辑处理。
- 记录解码请求状态、实际编码器、尝试和独立回退原因；renderer 还记录每个视频输入的计划。没有运行时硬件帧确认信息时写 requested_unconfirmed，任务详情显示“已请求硬件解码”，避免将请求参数等同于硬解成功。

### 集群兼容

成片集群沿用配置快照携带软件偏好；工作机接受任务时，本机开启的软件偏好也会强制软件处理。横竖转换工作机保持 conversion_protocol=2，并增加 conversion_codec_policy=1 能力声明。只有声明该能力的节点收到 software_codec_enabled 字段；主控开启强制软件模式时拒绝不支持该字段的旧工作机，避免其忽略偏好。新工作机仍接受旧请求格式，本机或主控任一方要求软件处理时使用软件模式。原超分集群编码协议本阶段不改变。
