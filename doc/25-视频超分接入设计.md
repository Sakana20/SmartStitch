# 视频超分接入设计：Real-ESRGAN CoreML 模型切换与回缩

状态：首版功能已实现；完整样片和正式打包验证待做。研究与实现日期：2026-09-23。

多机并行处理单条视频的接入方案见[视频超分接入渲染集群设计](26-视频超分接入渲染集群设计.md)。

## 1. 目标和首版范围

在工具台现有“超分”卡片内提供视频清晰化：默认用 Real-ESRGAN `x2plus` 做原生 2 倍超分，也可选择 `animevideo` 做原生 4 倍超分；两者最后都回缩到各自源视频的宽高。原视频保留，输出为独立文件。首版支持 macOS Apple Silicon 本机与渲染集群；不提供最终放大分辨率、自动锐化强度等选项。

**输出规格逐条取自源视频**：预检读取当前输入的宽度、高度与有理数帧率，并将这些值传入处理、编码和最终校验。1080×1920、24 fps 只是 H3 样片的规格，不是超分工具的固定输出预设。例如输入 320×180、10 fps，输出也应为 320×180、10 fps。首版输出封装与编码统一为 H.264 MP4，不要求沿用源视频的编码格式。

“更清晰”是预期用途，不保证所有素材都改善。压缩噪声、文字、皮肤和细线可能出现伪细节或涂抹；回缩后像素数量不增加。验收时必须用实际短视频在 100% 显示比例下比较原片和输出，不能仅以模型倍率判断效果。

## 2. 上游研究结论

来源：[hanxiao/real-esrgan-coreml](https://github.com/hanxiao/real-esrgan-coreml)；[视频脚本](https://github.com/hanxiao/real-esrgan-coreml/blob/main/video_upscale.py)、[推理与切块实现](https://github.com/hanxiao/real-esrgan-coreml/blob/main/upscale.py)、[模型发布页](https://github.com/hanxiao/real-esrgan-coreml/releases/tag/v1.0.0)、[依赖声明](https://github.com/hanxiao/real-esrgan-coreml/blob/main/pyproject.toml)。实际开发时固定一个已验证的上游提交及模型资产 SHA-256，不跟随 `main` 自动变化。

| 项目 | 研究结果与接入决定 |
| --- | --- |
| 模型 | 默认 `RealESRGAN_x2plus_522_fp16.zip`（原生 2 倍）；可选 `RealESRGAN_animevideo_522_fp16.zip`（原生 4 倍）。两者分别校验官方 ZIP 哈希与 CoreML 输入/输出形状。 |
| 推理 | CoreML，优先验证本机 `ALL` 计算单元；默认 tile 为 512，预填充为 10，模型输入应为 **522×522**。重叠区域沿用上游权重融合，初值 32。实际计算单元需按目标芯片测速，不能直接沿用上游视频脚本的 `CPU_AND_GPU`。 |
| 依赖 | `coremltools`、`numpy`、`Pillow`，以及已有的 FFmpeg/ffprobe。运行时不需要 PyTorch；不要把模型下载失败自动转为本地 PyTorch 转换。 |
| 模型位置 | 发布包内预置已校验模型，或由工具面板显式下载并校验后放到可写应用数据目录。不能写入只读 `.app` 资源目录，也不能未经用户感知在处理任务中隐式下载。首版推荐随 DMG 预置，以支持离线运行。 |
| 平台 | 上游针对 Apple Silicon；本项目当前 DMG 也只构建 macOS arm64。非支持平台需给出明确不可用提示。 |

### 欧美风格 3D 动漫素材的模型选择

对带立体光影、皮肤、头发和材质纹理的欧美风格 3D 动漫，默认选择 `x2plus`；对线条和平涂为主的 2D 动漫视频，可手动选择 `animevideo`。不凭“动漫”标签自动切换。`animevideo` 是原生 4 倍模型，先做 4 倍推理，再逐 tile 用 Lanczos 回缩到源视频尺寸并融合；3D 素材至少抽人脸、头发、材质和运动帧比较，不预设动漫视频模型一定更好。[CoreML 模型列表](https://github.com/hanxiao/real-esrgan-coreml#models)、[原项目动漫视频说明](https://github.com/xinntao/Real-ESRGAN/blob/master/docs/anime_video_model.md)。

上游 `video_upscale.py` 可以作推理逻辑参考，但不能直接作为成品视频命令调用：它默认使用 `x4plus`，输出倍率后的尺寸；它抽 PNG、重编码为 H.264，却没有把原音轨映射到输出，且按 `r_frame_rate` 重建时间线。它在 `process_frames_with_io()` 中把每帧的 float32 超分数组保存到 `outputs` 列表，长视频内存占用会持续增长。当前脚本还计算 `model_size = tile_size + PRE_PAD * 2`，默认得到 532，与已发布模型的 522 不一致；图片脚本则使用 `tile_size + PRE_PAD`。接入时应明确使用 522，并在加载前校验模型输入形状。上述判断来自对上游当前源码的检查，最终实现还需用固定提交做端到端验证。

上游 README 标注代码 MIT、权重来源 BSD-3；但仓库当前未提供独立 `LICENSE` 文件。发布前需确认确切代码授权文本和模型再分发条件，记录来源、版本、哈希并补充本项目 `THIRD_PARTY_NOTICES.md` 及 DMG 的许可材料。上游 M3 Ultra 的 512×512 单图 `x2plus` 约 0.12 秒只是参考数据，不能用来承诺本机视频帧率。

## 3. 用户操作和输出约定

1. 点击工具台“超分”卡片。本机模式选择**一个视频文件**和输出文件夹；集群模式固定扫描 NAS `超分/原素材` 第一层视频，将结果写入 `超分/已处理`，无需选择主控本机文件夹。预检展示每条源视频的宽高、帧率、帧数与待处理/已有结果/无效数量。
2. 显示 `x2plus` / `animevideo` 模型选择及其原生倍率，最终都输出源视频尺寸。用户点击开始后在面板查看准备模型、解码、超分、编码、完成等阶段，以及已处理帧数和当前文件。
3. `x2plus` 输出命名为 `<原名>_SR2x_原尺寸.mp4`；`animevideo` 命名为 `<原名>_SR_animevideo_原尺寸.mp4`。目标已存在时依次使用 `_2`、`_3` 后缀，不覆盖。输出文件夹可与输入相同，但源文件永不修改。
4. 使用临时文件写入，探测输出成功且关键属性符合预期后原子改名；失败或取消删除临时视频和任务临时目录。进度面板可取消；离开工具面板或刷新后可恢复查看最近任务。退出桌面应用时计入运行任务提示并终止处理。
5. 首版接受可由 FFmpeg 解码、具有恒定帧率的普通单视频轨素材，支持 MP4、MOV、M4V、MKV。无视频轨、损坏文件、可变帧率、多视频轨、附带旋转矩阵而无法确认显示尺寸的输入应在预检阶段明确拒绝或经专门处理后才开放。视频 Alpha、HDR、10-bit、隔行扫描和字幕/附加数据轨不承诺保留，预检需提示或拒绝，避免静默丢失。

首版输出 H.264、`yuv420p`、MP4，保持输入的**显示宽高、帧数、时长与播放速度**；音频存在时保留声音与同步。原尺寸若不满足 4:2:0 偶数宽高，预检拒绝并解释原因，避免偷偷改变宽高。音频可在封装兼容时复制，否则转 AAC；不能把音频丢弃。没有音频的输入保持无音频。

## 4. 处理管线

```text
ffprobe 预检 → 加载并校验用户选择的 CoreML 模型
    → FFmpeg 解码为 RGB 帧（有界队列）
    → 512 tile + 10 预填充 + 32 重叠 → CoreML 2×/4× → 按模型倍率回缩并融合
    → 每帧缩回输入显示宽高（固定 Lanczos）→ 8-bit RGB
    → FFmpeg H.264 编码并合入原音频 → 临时 MP4
    → ffprobe 验证 → 原子发布目标文件
```

- 解码、推理、编码之间采用有界队列/流式管道，不在磁盘保存全部 PNG，也不保存全部 float32 输出数组。首版一次只运行一个超分任务，限制内存与 GPU 争用。若模型或 FFmpeg 失败，向前端返回具体阶段与错误，不报告成功。
- 缩放**在高分辨率 RGB 图像上、进入有损编码前**完成。`x2plus` 整帧融合后回缩，`animevideo` 逐 tile 回缩后融合，以免 4 倍整帧浮点缓存占用过大；两种路径的接缝与运动画质需分别验收。
- 编码参数首版建议 `libx264 -crf 18 -preset medium -pix_fmt yuv420p`，以画质优先；具体参数经样片验证后固化。`-movflags +faststart` 便于预览。颜色范围/矩阵和旋转元数据需按预检结果处理，不能只读 coded width/height。
- 帧时间以预检确认的 CFR 有理数帧率处理，不使用浮点数重建。实际视频帧数、音频长度和 A/V 偏移需端到端校验。VFR 应明确拒绝，后续若要支持则按原始每帧 PTS 设计专门路径，不能仅取 `r_frame_rate`。
- 资源估算按输入尺寸、tile 数和所选模型倍率计算。临时目录位于可写空间且随任务清理；开始前检查可用空间。模型加载、首帧推理和视频解码分别报告进度或状态，避免首帧长时间无反馈。

## 6. 验收与实施顺序

1. 固定上游提交和模型 ZIP，校验 SHA-256、522 输入形状、模型许可及离线加载；用一张图验证确实产生 2 倍尺寸，再回缩至原尺寸。
2. 用 5–10 秒的 720p/1080p、横竖屏、带/不带音频样片跑完整管线。核对宽高、帧数、帧率、时长、音轨、起始同步，并人工比较纹理、文字、脸部、运动边缘和块接缝。记录处理耗时、峰值内存与临时空间。
3. 验证异常路径：缺模型、断网、模型损坏、磁盘不足、无法解码、VFR、奇数尺寸、同名输出、处理中取消、应用退出。任何失败均不得覆盖源文件或留下冒充成功的目标文件。
4. 完成 API 与工具面板接入，核对任务刷新后的状态、取消反馈和桌面退出提示；最后在正式 arm64 打包流程中验证离线机器可启动、CoreML 可加载、签名通过、第三方许可齐全。

以上为最初的验收计划；当前代码实现与验证进度见第 8 节。

## 7. 2026-09-23 单帧模型初测

- 样本：用户提供的 H3 数字人视频 `V20260910000261_baseline_1080p.mp4`，1080×1920、24 fps、约 15.08 秒、362 帧，H.264 视频和 AAC 音频。取 5 秒处的一帧，分别裁出人脸与字幕/衣服区域，各 512×512。
- 模型：官方 v1.0.0 `RealESRGAN_x2plus_522_fp16.zip`，本次下载文件的 SHA-256 为 `4acf0afa2828e82b88e1d712b4b7604977698c99aa1505276c943922be6b3938`。CoreML 读取到输入 `[1,3,522,522]`、输出 `[1,3,1044,1044]`。
- 方法：裁块右侧和底部各做 10 像素反射填充，使用 `coremltools 9.0` 的 `CPU_AND_GPU` 实际推理；去掉输出填充后得到 1024×1024，再用 Pillow 12.3 的 Lanczos 缩回 512×512。
- 性能：本机为 16 GB Apple M4 Mac mini。受限进程内重复推理约 2.5 秒/块，且退出时出现 CoreML 缓存目录权限提示；正常进程权限下，`CPU_AND_GPU` 的稳定速度约 0.83–0.88 秒/块。后续同机同裁块对照中，`ALL` 为 0.18–0.19 秒/块，`CPU_ONLY` 为 1.17–1.22 秒/块。`ALL` 相对 `CPU_AND_GPU` 约快 4.5 倍；目前只确认速度差异，未证明具体是 GPU 还是 ANE 执行。1080×1920 按当前 512/32 切块为 12 块，实测同一整帧 12 次 `ALL` 推理合计 2.23 秒；362 帧粗算仅推理约 13–14 分钟，未计解码、融合和编码。正式接入前仍需跑连续视频基准。
- 一致性：同一人脸裁块用 `ALL` 和 `CPU_AND_GPU` 分别推理，2 倍输出的 8-bit 像素平均绝对差约 0.087/255、最大差 2/255；回缩后平均绝对差约 0.135/255、最大差 2/255。此小样未见明显画质差异，但仍需验证视频连续帧。
- 结果：两个裁块都成功生成，原尺寸前后每通道平均绝对像素差约 2.9/255。100% 观看时，人脸的发丝、眼部和字幕边缘更硬朗；皮肤及衣服的平滑感也更明显，字幕阴影可能变重。需要用连续视频确认运动时是否闪烁，以及全帧切块接缝是否可见。
- 对比文件在本机 `output/sr-model-test/h3-face-compare.png` 和 `output/sr-model-test/h3-subtitle-compare.png`，左侧原图、右侧 2 倍超分后回缩。目录被 `.gitignore` 排除，不属于发布素材。此次测试未处理整段视频、未验证音频/封装/时序，也未接入界面。

## 8. 当前实现与最小化验证

- 工具台“超分”卡片已经接入源视频选择、输出目录、`x2plus`/`animevideo` 切换、按所选模型下载/校验、预检、本机/集群选择、进度和取消。API 与桌面退出统计也已接入。运行依赖为 `coremltools`、NumPy、Pillow、FFmpeg；两个模型分别固定官方 v1.0.0 ZIP 的 SHA-256，首次在每台工作机按需下载。模型不上传到外部推理服务。
- 本机使用 `CoreML ComputeUnit.ALL`，512 像素 tile、32 像素重叠和 10 像素预填充；`x2plus` 在整帧 2 倍融合后回缩，`animevideo` 为控制内存而逐 tile 做 4 倍推理、回缩后融合。输出固定 H.264/yuv420p MP4，原音频转 AAC，最终核对尺寸、帧数和音轨。当前接受单视频轨、偶数宽高、8-bit yuv420p、CFR、非 HDR、无旋转元数据的 MP4/MOV/M4V/MKV。
- 用用户给出的 1080×1920 H3 视频实际处理 `[0,2)` 和 `[2,4)` 两段，共 4 帧；两个片段无音轨、原尺寸，FFmpeg 无损拼接后为 4 帧，并成功接回 AAC 音频。再用这个 4 帧有声样片走本机 `VideoUpscaleManager` 全流程，任务完成，输出仍是 1080×1920、24 fps、4 帧、AAC 音轨，耗时约 15 秒。受限命令环境会阻止 CoreML 在系统临时目录编译模型；在正常 macOS 权限下推理通过。此验证只覆盖 4 帧，**还未证明完整 362 帧的运动画质、长时间稳定性或端到端耗时**。
- 另用 320×180、10 fps、2 帧、有音频的横屏样片运行真实 CoreML 本机任务；输出仍为 320×180、10 fps、2 帧、有音频，确认不会强制套用 H3 样片的 1080×1920、24 fps。
- 选择 `animevideo` 后，官方 v1.0.0 资产 `RealESRGAN_animevideo_522_fp16.zip` 的 SHA-256 为 `0e83446f03b4c0a60c970da02d70d10af14949c169714f9ad8e8ea3e479b145b`；用同一 320×180、10 fps、2 帧有音频样片实际完成原生 4 倍 CoreML 推理及回缩，最终规格与源视频一致。模型间画质优劣仍需真实 2D/3D 素材人工比较。
- 本机任务目前保存在进程内，App 退出后无法恢复本机进度；集群任务另存 SQLite。正式 arm64 App/DMG 的 PyInstaller CoreML 收集、签名及离线运行仍需实际构建验证。上游权重与代码的最终发布许可审查仍需完成。
