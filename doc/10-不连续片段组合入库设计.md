# SmartStitch 不连续片段组合入库设计

> 实现状态：已于 2026-09-16 完成第一版实现与回归验证。前端已支持合并、统一分类、组号标识和拆分；后端已支持 `segment_indexes` 以及 FFmpeg `trim/atrim + concat`。组合内单个成员的独立移除按本文扩展方案保留，当前可先“拆分”后移除指定条目。

## 1. 背景与目标

当前“片段列表”中的每一行都对应一个连续帧区间，后端也按“一行生成一个 MP4”执行切片。当一条可复用素材由两个不连续区间组成时，例如需要保留片段 02 和片段 05、删除中间内容，现有流程只能生成两个文件，不能把它们作为一个素材入库。

本设计新增“组合片段”：

- 用户可以把两个或多个已标记片段组合成一个逻辑输出。
- 组合成员可以不连续，中间未选择的画面和声音完全丢弃。
- 最终只生成一个 MP4，并只选择一次入库类型。
- 原始断点、审核片段和源视频保持不变；组合只属于本次待切片清单。
- 普通单片段切片继续保持现有行为，旧请求可兼容迁移。

第一版仅支持同一个原视频、同一个审核版本内的片段组合，不支持跨视频合并，也不提供转场、淡入淡出或自定义成员顺序。

## 2. 核心定义

- **源片段**：断点之间的连续半开帧区间 `[start_frame, end_frame)`，仍由后端审核记录派生。
- **输出单元**：点击“切割并入库”后生成一个正式 MP4 的最小任务单位。
- **单片段输出**：只包含一个源片段的输出单元，与当前行为一致。
- **组合片段输出**：包含两个或多个源片段的输出单元，各成员可以不连续。
- **被排除间隙**：组合成员之间未被选择的源视频区间，不进入输出文件。

示例：

```text
源时间线：  [片段 01][片段 02][片段 03][片段 04][片段 05][片段 06]
用户选择：            ███████                         ███████
组合成员：             片段 02                         片段 05
最终输出：  [片段 02][片段 05]
```

组合不等于扩大范围。系统不得把它错误实现为从片段 02 开始一直切到片段 05 结束，否则会把片段 03、04 一并带入。

## 3. 产品交互

### 3.1 片段列表

片段列表每行增加一个独立复选框，用于选择“要组合的条目”。行本身的点击仍只负责定位播放头，不能兼作多选，以免和当前预览操作冲突。

当勾选两个或更多条目时，列表工具栏启用：

```text
[合并所选（2）] [取消选择]
```

点击“合并所选”后：

1. 按源时间线的帧顺序排列成员。
2. 将多个普通行收拢为一个“组合片段”卡片。
3. 卡片显示成员编号、各自时间范围、合计时长和被排除间隙数量。
4. 卡片只保留一个类型选择器和一个“切割并入库”输出身份。

建议展示：

```text
┌ 组合 01 · 2 段 · 合计 06.400 s · 跳过中间 2 段 ───────────────┐
│ 02  00:00:02:46 → 00:00:05:20                              │
│ 05  00:00:11:08 → 00:00:14:52       [利益点 1 ▾] [拆分] [移除] │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 分类规则

- 分类属于输出单元，不属于组合中的单个成员。
- 两个成员合并后只选择一次前贴、引子、利益点、结尾、尾帧或未归类。
- 如果被合并条目的分类完全相同，组合后保留该分类。
- 如果分类不同，或存在未分类成员，组合后的分类重置为“选择类型”，要求用户重新确认。
- 一个源片段在同一份草稿中最多属于一个输出单元，不能同时单独切片又成为另一个组合的成员。

### 3.3 顺序规则

第一版固定按 `start_frame` 从小到大拼接，保证结果符合原视频叙事顺序。用户勾选的先后顺序不改变成片顺序。

暂不支持拖动成员改序。若后续确实需要倒序或自定义顺序，应单独增加显式排序功能，不能暗中使用点击顺序。

### 3.4 拆分和移除

- “拆分”：把组合恢复成多个普通输出单元，并将组合分类复制给各成员。
- 从组合中移除一个成员：剩余成员不少于两个时继续保持组合；只剩一个时自动降级为普通单片段输出。
- 移除组合：从待切片清单中移除所有成员，不影响时间线断点和源视频。
- 已经完成入库的组合不会因为前端拆分而删除成品；再次执行属于一个新的切片请求。

### 3.5 时间线反馈

- 同一组合的成员使用相同轮廓颜色，并显示相同组号，例如 `G1`。
- 不连续成员之间不绘制实心色块，避免误导用户认为中间内容会被保留。
- 可以用细虚线或组号表达关联，但虚线不得遮挡断点和播放头。
- 摘要从“3 个已标记”扩展为“3 个输出片段 · 5 个源区间”，明确最终文件数量和原始选择数量。

## 4. 前端状态模型

当前 `queuedSegmentIds + segmentCategories` 无法表达多对一关系，建议统一替换为输出单元列表：

```json
{
  "sliceUnits": [
    {
      "client_unit_id": "unit-01",
      "segment_ids": ["f000000166-f000000320"],
      "category": "hook"
    },
    {
      "client_unit_id": "unit-02",
      "segment_ids": [
        "f000000420-f000000610",
        "f000000980-f000001174"
      ],
      "category": "benefit_1"
    }
  ],
  "mergeSelection": []
}
```

约束：

- `sliceUnits` 的一项对应一个最终 MP4。
- `segment_ids` 长度为 1 时是普通片段，大于 1 时是组合片段。
- 所有 `segment_ids` 在整份草稿中唯一。
- `mergeSelection` 只是临时界面选择，不写入切片请求。
- 前端显示仍使用稳定的帧区间 `segment_id`；提交时转换成审核版本中的 `segment_index`。

现有页面状态可在加载时迁移：每个 `queuedSegmentId` 转换成一个单成员 `sliceUnit`，对应分类原样带入，因此普通使用流程不会变化。

## 5. 断点变化时的安全规则

组合必须继续遵守“审核版本是权威数据”的原则。

- 组合所有成员的开始帧和结束帧均未变化：保留组合和分类。
- 任一成员因移动、新增或删除断点而消失：不得用旧索引套用新片段。
- 第一版采用安全策略：受影响的组合自动拆散；仍完全未变的成员保留为普通片段，受影响成员从清单移除，并提示“组合边界已变化，请重新选择”。
- 新派生的片段不会自动加入原组合。
- 任意断点变化都会使 `review_revision` 失效，执行前仍须保存最新审核版本。

这样可以保留未受影响的用户选择，同时避免旧组合静默指向错误画面。

## 6. API 设计

### 6.1 新请求结构

`POST /api/v1/timeline/slices` 保留现有地址，将 assignment 从单索引扩展为索引数组：

```json
{
  "analysis_id": "0123456789abcdef01234567",
  "config_id": "product-library",
  "review_revision": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "current_config_hash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "assignments": [
    {
      "client_unit_id": "unit-01",
      "segment_indexes": [2],
      "category": "hook"
    },
    {
      "client_unit_id": "unit-02",
      "segment_indexes": [5, 8],
      "category": "benefit_1"
    }
  ],
  "client_request_id": "1fbd890c-7693-45fc-955a-3f652cf50ace"
}
```

后端不信任前端提交的时间值。它只接受索引，再从与 `review_revision` 匹配的审核记录中读取权威 `start_frame` 和 `end_frame`。

### 6.2 兼容旧请求

为避免现有前端或未完成请求立即失效，后端在一个迁移周期内兼容：

```json
{"segment_index": 2, "category": "hook"}
```

加载边界将其规范化为：

```json
{"segment_indexes": [2], "category": "hook"}
```

新前端只发送 `segment_indexes`。同时提交 `segment_index` 和 `segment_indexes` 时返回 `422`，不猜测优先级。

### 6.3 后端预检

启动任何 FFmpeg 进程前一次性完成：

1. assignments 非空，每个 `segment_indexes` 包含 1～20 个索引。
2. 同一 assignment 内索引不重复，后端按权威开始帧排序。
3. 同一个源片段不能出现在两个 assignment 中。
4. 所有索引均属于当前 `review_revision`。
5. 每个成员区间合法、非空且互不重叠。
6. 所有成员来自同一个 `analysis_id` 和源视频指纹。
7. 分类仍存在，目标目录位于健康的受管视频库内。
8. 配置哈希、源视频指纹、磁盘空间和输出冲突规则均通过。

任一预检失败时整批不启动 FFmpeg，避免只生成部分组合后才发现结构错误。

## 7. FFmpeg 实现

### 7.1 单片段

`segment_indexes` 只有一个成员时继续使用现有精确重编码切片路径，不增加额外拼接开销。

### 7.2 组合片段

组合成员来自同一个源文件，画面尺寸、帧率和音轨结构天然一致。推荐用单次 FFmpeg `trim/atrim + concat` 滤镜生成一个输出文件，不先产生多个正式切片：

```text
[0:v]trim=start_frame=S1:end_frame=E1,setpts=PTS-STARTPTS[v0];
[0:a]atrim=start=T1:end=U1,asetpts=PTS-STARTPTS[a0];
[0:v]trim=start_frame=S2:end_frame=E2,setpts=PTS-STARTPTS[v1];
[0:a]atrim=start=T2:end=U2,asetpts=PTS-STARTPTS[a1];
[v0][a0][v1][a1]concat=n=2:v=1:a=1[v][a]
```

输出映射：

```text
-map [v] -map [a]
-c:v libx264 -preset fast -crf 18
-c:a aac -movflags +faststart
```

源视频没有音轨时使用纯视频分支：

```text
[v0][v1]concat=n=2:v=1:a=0[v]
```

实现要求：

- 视频按审核帧号执行 `trim`，每段通过 `setpts=PTS-STARTPTS` 从零开始。
- 音频按对应时间执行 `atrim`，每段通过 `asetpts=PTS-STARTPTS` 重置时间戳。
- 成员之间采用硬切，不插入黑帧、静音、转场或交叉淡化。
- 最终期望时长是各成员时长之和，不是首成员开始到末成员结束的包络时长。
- FFmpeg 命令继续使用参数数组执行，不通过 shell 拼接用户路径。
- 输出先写同目录唯一 `.part.mp4`，成功并通过 ffprobe 后再原子改名。
- FFmpeg 失败时清理 `.part`，不会留下各成员的正式中间文件。

对当前按固定 FPS 分析的素材：

```text
part_duration = (end_frame - start_frame) / fps
expected_duration = sum(part_duration)
```

VFR 素材仍沿用现有限制；后续引入真实 PTS 索引时，将审核段映射为 PTS 后再传给音视频 trim。

### 7.3 校验

ffprobe 校验至少包含：

- 文件存在且非空。
- 至少包含一个视频流。
- 有音频的源视频生成的组合仍包含音频流。
- 输出时长接近各成员时长之和，建议容差为 `max(2 / fps, 0.08 秒)`。
- 输出时长不得接近从第一段开始到最后一段结束的包络时长，以测试中间间隙确实被删除。

## 8. 文件名与切片清单

组合文件名保持简洁，不把所有帧区间塞进文件名：

```text
source__g001_benefit-1_p002-005.mp4
```

- `g001`：本批第一个组合输出。
- `p002-005`：首尾成员序号，只用于快速辨识。
- 完整成员和帧区间必须写入清单，文件名不是权威数据。

清单条目示例：

```json
{
  "unit_index": 1,
  "client_unit_id": "unit-02",
  "category": "benefit_1",
  "segment_indexes": [5, 8],
  "segment_ids": [
    "f000000420-f000000610",
    "f000000980-f000001174"
  ],
  "parts": [
    {"start_frame": 420, "end_frame": 610, "duration_seconds": 3.166667},
    {"start_frame": 980, "end_frame": 1174, "duration_seconds": 3.233333}
  ],
  "total_duration_seconds": 6.4,
  "excluded_gap_frames": 370,
  "output_path": "/视频库/切片素材/利益点/1/source__g001_benefit-1_p005-008.mp4",
  "status": "succeeded",
  "error": null
}
```

批次的 `success_count` 和 `failure_count` 按输出单元计数，不按源片段数量计数；另增加 `source_segment_count` 便于审计。

## 9. 幂等、失败和恢复

- 继续以 `client_request_id + analysis_id + review_revision + config_id` 识别同一批请求。
- 相同请求重试直接返回原清单，不重复生成组合视频。
- 单个组合失败时，该输出单元记为失败；已经成功的其他输出单元保留。
- 组合失败不会回退为多个单片段文件，因为这会改变用户确认的输出语义。
- 新请求遇到同名文件时沿用 `-v2`、`-v3` 冲突策略，不覆盖已有素材。
- 服务中断后，清单中 `running` 的条目标记为 `interrupted`；残留 `.part` 可在恢复或清理流程中安全删除。

## 10. 测试矩阵

| 场景 | 预期 |
|---|---|
| 片段 02 与 05 组合 | 只生成一个 MP4，顺序为 02 → 05 |
| 中间存在两个未选择片段 | 输出中不包含中间画面和声音 |
| 组合两个相邻片段 | 生成一个连续 MP4，行为与合并范围一致 |
| 组合成员点击顺序相反 | 仍按源时间顺序输出 |
| 单片段和组合片段混合提交 | 每个 assignment 生成一个文件并进入正确目录 |
| 同一源片段加入两个组合 | 全批预检失败，FFmpeg 不启动 |
| 组合包含不存在的索引 | 返回审核版本错误，不生成文件 |
| 组合成员分类原本不同 | 前端合并后分类清空，必须重新选择 |
| 源视频无音频 | 使用纯视频 concat，结果可播放 |
| 源视频有音频 | 拼接点前后音画同步，输出保留音轨 |
| 移动其中一个成员边界 | 组合自动拆散并提示重新选择 |
| 组合中途 FFmpeg 失败 | 清理 `.part`，不产生成员正式文件 |
| 相同请求重试 | 返回同一清单，不重复入库 |
| 时长校验 | 输出时长等于成员时长之和而非包络时长 |

测试素材应让不同片段具有明显不同的颜色、画面编号和音调，从而同时验证顺序、中间间隙删除以及音频拼接结果。

## 11. 实现顺序

1. 先将前端待切片状态迁移为 `sliceUnits`，保持所有单片段行为不变。
2. 增加列表复选框、“合并所选”、组合卡片和拆分操作。
3. 扩展请求模型为 `segment_indexes`，实现旧 `segment_index` 的兼容归一化和全批预检。
4. 重构后端任务构建逻辑，使清单的一项代表一个输出单元。
5. 新增 `_render_composite_slice`，完成有音频和无音频两种 FFmpeg filter graph。
6. 增加组合时长、流信息和 `.part` 原子提交校验。
7. 补齐前端状态、API、FFmpeg 集成、失败恢复和幂等测试。
8. 完成回归后再移除旧请求字段兼容，不与第一版同时删除。

## 12. 验收标准

1. 用户能在片段列表选择至少两个不连续条目并合并为一个组合片段。
2. 组合卡片明确显示全部成员、合计时长、排除间隙和唯一分类。
3. 时间线能辨认哪些不连续区间属于同一组合，但不会把中间区间着色为已选择。
4. 一个源片段不能同时属于多个输出单元。
5. 点击“切割并入库”后，一个组合只产生一个正式 MP4。
6. 输出只按原时间顺序包含组合成员，中间未选择内容完全不存在。
7. 单片段、未归类、动态利益点、库路径安全、审核版本和配置哈希规则全部保持有效。
8. 断点改变后不会静默复用已经失效的组合成员。
9. 清单能追溯组合的全部源片段、帧区间、总时长和输出位置。
10. FFmpeg 失败、任务重试和进程中断不会留下正式半成品或重复入库文件。
