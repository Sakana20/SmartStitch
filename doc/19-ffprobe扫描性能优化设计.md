# ffprobe 扫描性能优化设计

## 1. 文档状态

- 状态：首版已实现（2026-09-20）。
- 日期：2026-09-20。
- 范围：配置素材扫描、计划预览和任务创建过程中调用的 `ffprobe`；不改变切片、渲染结果校验和视觉边框透明像素抽样逻辑。
- 目标：在保持现有素材校验完整性的前提下，缩短首次扫描和重复扫描等待时间。

## 2. 当前问题与基线

优化前的 `scan_config()` 按素材组顺序调用 `scan_group()`，每个素材组内部再按文件顺序同步执行 `probe_media()`。每个文件都会单独启动一次 `ffprobe` 子进程，扫描结果没有写入内存或持久化缓存。

同一份素材还会在下列入口重复扫描：

1. 用户点击“重新扫描”。
2. 用户预览组合计划。
3. 用户创建生成任务。

2026-09-20 在当前外接盘素材库上的只读基准：

| 场景 | 素材数 | 并发数 | 耗时 |
|---|---:|---:|---:|
| 当前完整扫描 | 126 | 1 | 14.905 秒 |
| 使用相同 `probe_media()` 的并发验证 | 125 | 8 | 3.238 秒 |
| 首版实现后的冷扫描 | 126 | 8 | 4.832 秒 |
| 首版实现后的暖扫描 | 126 | 缓存命中 | 0.016 秒 |

独立并发验证约为原串行实现的 4.6 倍；完整首版冷扫描约提升 3.1 倍，暖扫描约提升 900 倍。前两次计时的素材数相差 1，是因为完整扫描还包含固定风险提示语图片；不影响视频素材并发结论。该数据是本机单次实测，不作为所有磁盘和 NAS 环境的固定性能承诺。

当前 `ffprobe` 已通过 `-show_entries` 只请求业务需要的容器和流字段，没有执行逐帧计数。主要耗时来自串行子进程启动、外接存储访问和重复探测，而不是 JSON 字段过多。

## 3. 目标与非目标

### 3.1 目标

- 冷扫描只对缓存未命中的文件执行 `ffprobe`，并受控并发。
- 文件未变化时，重复扫描直接复用持久化结果。
- 文件内容可能变化时自动失效，不能返回已知过期的流信息。
- 单个损坏文件、慢盘或异常挂载不能无限阻塞整批扫描。
- 扫描结果的文件顺序、错误归属和业务校验规则与当前行为一致。
- 旧配置无需修改即可使用默认优化参数。

### 3.2 非目标

- 不取消逐个素材校验，也不根据同目录抽样结果推断其他文件规格。
- 不用扩展名、文件名或历史同类素材代替 `ffprobe`。
- 首版不使用内容全量哈希；读取整个视频计算哈希会抵消扫描优化收益。
- 首版不通过激进缩小 `-probesize` 或 `-analyzeduration` 换取速度，避免漏检后置音轨、特殊封装或较晚出现的流信息。
- 不复用成片、切片输出后的完整性校验结果；输出文件仍需独立验证。

## 4. 总体方案

扫描分为“发现与指纹”“缓存查询”“并发探测”“稳定组装”四个阶段：

```text
枚举候选文件
  │
  ├─ stat：绝对路径、大小、mtime_ns
  │
  ▼
批量查询 SQLite 探测缓存
  │
  ├─ 命中：直接还原 MediaProbe
  └─ 未命中/已失效：进入有界线程池
                         │
                         ▼
                    ffprobe 子进程
                         │
                         ▼
                   回写成功或短期失败
  │
  ▼
按原有路径顺序组装 Asset 和 ScanResult
```

首版同时实现持久化缓存和有界并发。仅增加并发只能改善当次扫描，不能解决预览和任务创建的重复探测；仅增加缓存则不能改善第一次扫描，因此两者不可互相替代。

## 5. 缓存设计

### 5.1 存储位置

缓存写入现有本机运行数据库 `data/smartstitch.db`，新增独立表 `media_probe_cache`。缓存不写入素材目录、项目 YAML 或 NAS 共享配置，不参与项目同步，也不提交版本控制。

每台 SmartStitch 服务维护自己的缓存，避免多台机器因 FFmpeg 版本、挂载路径或文件可见性不同而共享错误结论。

### 5.2 文件指纹

缓存命中的必要条件为以下字段全部一致：

- 规范化绝对路径。
- `st_size`。
- `st_mtime_ns`，不得降级为秒级 `st_mtime`。
- 探测配置版本 `probe_schema_version`。
- `ffprobe` 能力签名，包括可执行文件路径和版本。
- 探测 profile。视频和图片使用不同 profile；图片 profile 还必须包含配置的 `image_duration_seconds`，或在缓存外重新覆盖该业务时长。

只要任一字段变化，就视为缓存未命中。缺失文件不进入持久化缓存，避免外接盘临时未挂载时污染后续结果。

首版不依赖 inode 作为必需字段：部分 NAS 和外接文件系统的 inode 稳定性不足。实现可以把设备号和 inode 保存为诊断字段，但不能仅凭它们复用结果。

### 5.3 表结构

建议字段如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `path` | TEXT | 规范化绝对路径 |
| `size_bytes` | INTEGER | 文件大小 |
| `modified_at_ns` | INTEGER | 纳秒级修改时间 |
| `probe_profile` | TEXT | 视频/图片及相关参数签名 |
| `probe_schema_version` | INTEGER | 解析字段和语义版本 |
| `ffprobe_signature` | TEXT | ffprobe 路径与版本签名 |
| `status` | TEXT | `passed` 或 `failed` |
| `probe_json` | TEXT | `MediaProbe` JSON；失败时为空 |
| `error_text` | TEXT | 规范化错误摘要 |
| `checked_at` | TEXT | 最近探测时间 |
| `failure_expires_at` | TEXT | 失败缓存的过期时间 |
| `last_used_at` | TEXT | 最近命中或写入时间，用于后台清理 |

主键可使用 `(path, probe_profile)`。查询缓存后仍必须比较其余指纹字段，不把文件大小或修改时间拼入路径主键，以便同一路径更新时覆盖旧记录。

### 5.4 成功与失败缓存

- 成功结果在文件指纹、探测 profile、解析版本和 ffprobe 能力签名未变化时持续有效。
- 媒体结构错误等失败结果允许短期缓存，建议默认 60 秒，防止用户连续点击时反复启动同一个必然失败的子进程。
- 超时、权限、I/O、挂载中断等运行环境错误只允许短期缓存，不能在文件未变化的情况下永久失败。
- 失败缓存过期后重新探测；文件指纹变化时立即失效，不等待过期时间。
- 缓存记录损坏、JSON 无法解析或字段版本不兼容时，删除或覆盖该条记录并正常重新探测，不能让缓存故障阻止扫描。

### 5.5 清理策略

- 每次服务启动或后台维护时，删除超过 30 天未命中的记录。
- 可设置总记录上限，例如 100,000 条；超过上限时优先删除最久未使用记录。
- 不在每次扫描前遍历全表清理，避免把缓存维护变成新的前台延迟。
- 后续可增加“清除媒体扫描缓存”诊断接口，但不是首版前置条件。

## 6. 并发与超时

### 6.1 并发模型

`ffprobe` 是独立子进程且主要等待进程启动和存储 I/O，使用 `ThreadPoolExecutor` 管理即可，不需要在 Python 内进行视频解码。

- 默认 `probe_concurrency = 8`。
- 允许配置范围为 1～16；设为 1 时可用于诊断或兼容极慢 NAS。
- 线程池只接收缓存未命中的唯一文件，同一路径在多个素材组出现时只探测一次，再映射回各自的 `Asset`。
- 并发任务完成顺序不能影响返回顺序；最终仍按现有路径不区分大小写排序组装结果。
- 缓存命中结果与新探测结果必须经过同一套 `MediaProbe` 和业务有效性校验。

外接机械盘或繁忙 NAS 不一定在 16 路并发下更快。默认 8 来自当前素材库实测，后续应以 4、8、16 三档真实素材基准决定是否调整，而不是直接使用 CPU 核数。

### 6.2 单文件超时

- 默认单个 `ffprobe` 超时建议为 15 秒，可配置范围 3～120 秒。
- 超时后终止并回收子进程，将该素材标记为不可用并保留明确错误，例如“ffprobe 超时（15 秒）”。
- 一个文件超时不取消其他文件的探测。
- 请求级别不再额外串行重试；用户修复文件、重新挂载或失败缓存过期后再探测。

### 6.3 配置兼容

在 `scanner` 下新增可选字段，旧配置由默认值补齐：

```yaml
scanner:
  recursive: false
  ignore_hidden_files: true
  ignore_prefixes: ["._", ".~"]
  ignore_names: [".DS_Store"]
  probe_cache_enabled: true
  probe_concurrency: 8
  probe_timeout_seconds: 15
  probe_failure_ttl_seconds: 60
```

这些字段只控制性能和故障隔离，不改变允许扩展名、必需素材组、权重、命名解析或音轨判断规则。

## 7. 请求链路与一致性

重新扫描、计划预览和任务创建仍可各自调用 `scan_config()`，但第二次及后续调用应命中缓存，只承担目录枚举、`stat` 和结果组装成本。

首版不直接复用前端持有的扫描响应创建任务，因为从扫描完成到任务创建之间文件可能被替换。任务创建仍重新枚举和比较指纹；缓存只有在文件未变化时才命中。

如果缓存优化后重复请求仍存在明显目录遍历延迟，可在第二阶段增加短生命周期 `scan_token`：

- token 必须绑定配置内容哈希、目录清单指纹和服务实例。
- 任务创建使用 token 前仍检查所选文件的大小和修改时间。
- token 过期或指纹不一致时回退到正常扫描。

`scan_token` 不是首版要求，不能代替文件级 ffprobe 缓存。

## 8. 可观测性

每次扫描至少记录以下结构化指标：

- 候选文件总数。
- 缓存成功命中数、失败命中数和未命中数。
- 实际启动的 ffprobe 数量。
- 超时和探测失败数量。
- 使用的并发数。
- 目录枚举、缓存查询、ffprobe 和总耗时。

开发或诊断响应可增加可选的 `diagnostics` 字段；正式前端无需逐文件展示缓存细节，但可以在扫描摘要中显示“126 个素材，其中 124 个复用缓存”。日志不得打印素材内容、完整环境变量或无关隐私信息。

## 9. 实施步骤

1. 为 `ScannerConfig` 增加带默认值的缓存、并发和超时参数。
2. 在现有 SQLite 初始化流程中创建 `media_probe_cache` 表及索引。
3. 把“执行 ffprobe”和“缓存查询/回写”拆成独立组件，保留 `probe_media()` 作为对外兼容入口。
4. 重构扫描器：先收集所有候选资产和文件指纹，再批量查询缓存。
5. 对唯一未命中项执行有界并发探测，捕获超时和单文件错误。
6. 按原顺序组装 `Asset`，继续执行命名、必需组、固定叠图和视觉边框校验。
7. 添加结构化扫描指标和调试日志。
8. 完成单元测试、并发一致性测试和真实外接盘基准。

视觉边框的 `ffprobe` 元数据可以使用同一缓存，但 `_contains_transparent_samples()` 的代表帧 Alpha 解码是另一种内容校验。首版不得因为命中媒体元数据缓存而跳过透明像素校验；后续若单独缓存 Alpha 抽样，必须使用独立 schema 和失效规则。

## 10. 测试矩阵

| 场景 | 预期结果 |
|---|---|
| 第一次扫描新素材库 | 所有唯一素材并发探测，结果与当前串行实现一致 |
| 不修改文件再次扫描 | `ffprobe` 调用数为 0，全部成功结果来自缓存 |
| 只修改一个文件 | 只重新探测该文件，其他文件命中缓存 |
| 文件大小相同但 `mtime_ns` 变化 | 缓存失效并重新探测 |
| 文件路径相同但 profile 变化 | 缓存失效并重新探测 |
| ffprobe 版本或探测 schema 变化 | 旧缓存不复用 |
| 同一文件被两个素材组引用 | 每轮最多启动一次 ffprobe，两组获得各自 Asset |
| 一个文件损坏 | 其他文件仍完成；损坏文件错误与原规则一致 |
| NAS 中删除一个曾保存过权重的文件 | 下次扫描不再返回该条目，素材数量直接减少；配置中残留的权重记录不显示为异常 |
| 一个文件探测超时 | 到时终止该子进程，整批继续完成 |
| 超时后立即重扫 | 短期复用失败；TTL 到期后重新尝试 |
| 外接盘暂时未挂载 | 返回现有目录错误，不写入永久失败缓存 |
| 缓存 JSON 损坏 | 忽略损坏记录并重新探测，不导致整批失败 |
| 并发任务乱序完成 | 最终资产顺序与当前串行扫描完全一致 |
| `probe_concurrency: 1` | 功能正确，可作为串行诊断模式 |
| 视觉边框元数据命中缓存 | 仍执行透明像素抽样校验 |

测试中应通过替换子进程执行器统计实际调用次数，不依赖真实等待时间判断缓存是否命中。并发上限测试必须证明同时运行数不会超过配置值。

## 11. 性能验收

在 2026-09-20 基准所用机器、外接盘和同一批约 126 个素材上，以连续三次测试的中位数验收：

- 冷扫描目标：不超过 5 秒。
- 暖扫描目标：不超过 1 秒。
- 暖扫描实际 `ffprobe` 调用数：0。
- 仅修改一个素材后的扫描：实际 `ffprobe` 调用数为 1。
- 优化前后 `ScanResult` 的素材路径、媒体信息、有效状态、错误和顺序一致。

CI 只验证行为、调用次数和并发上限，不设置真实秒数门槛；真实耗时受磁盘、NAS、系统缓存和并发负载影响，性能秒数只在指定基准环境中验收。

## 12. 风险与回退

| 风险 | 控制措施 |
|---|---|
| 缓存返回陈旧元数据 | 使用路径、大小、`mtime_ns`、profile、schema 和 ffprobe 签名共同失效 |
| NAS 并发过高反而变慢 | 并发可配置，保留并发 1 的诊断回退 |
| 失败被永久缓存 | 失败使用短 TTL，环境错误不永久保存 |
| 子进程卡死 | 单文件超时并确保进程回收 |
| 并发导致结果顺序变化 | 探测与结果组装分离，按原候选顺序组装 |
| 缓存数据库异常阻止扫描 | 缓存按可降级组件处理，失败时回退到直接探测 |
| 激进 ffprobe 参数漏检流 | 首版保持当前完整探测参数，不缩小分析范围 |

素材是否存在与媒体是否可读应区分处理：扫描时已经从 NAS 删除的普通素材直接从结果中消失；路径仍存在但 ffprobe 无法读取的文件继续保留并标记为“异常”，避免把损坏文件误判成正常删除。素材组目录整体不可用时仍按“目录不存在或外接磁盘未挂载”处理，不能静默清空素材库。

紧急回退时可通过 `probe_cache_enabled: false` 关闭缓存，通过 `probe_concurrency: 1` 恢复串行探测；无需回退其他扫描、计划或渲染能力。
