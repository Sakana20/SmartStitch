# SmartStitch 多机集群渲染可行性研究

> 2026-09-23。固定主控 App + 可上线/下线的工作 App 已落地首版；各机本地 SQLite，NAS 仅存素材和成片。尚未在真实双机环境做性能和故障验收。

## 结论

**可行，且无需在 NAS 安装数据库或其他服务。** 一台固定保持运行的 SmartStitch.app 担任主控，一次完成扫描、权重配额和随机计划；其他在线 App 各领取完整的一条成片，在本机调用现有 FFmpeg 渲染器。主控也可以同时渲染。各机继续使用自己的本机 SQLite。工作 App 可随时上线或下线，主控不做角色交接。

主控通过工作 App 提供的受认证集群接口读取其本机任务状态；工作 App 也主动向主控汇报进度与结果。**不要通过 SMB 直接打开另一台 Mac 的 `smartstitch.db`**。数据库的文件锁、进程生命周期和本机路径都不适合这样使用；现有数据库还启用了 SQLite WAL，其跨主机共享数据库文件不受支持。

## 当前代码基础

| 能力 | 当前实现 | 集群改造 |
| --- | --- | --- |
| 批次计划 | `JobManager.create()` 一次完成素材扫描、配额、随机选择、命名，并把每条选择写入任务记录 | 主控只规划一次；将每条计划作为独立执行单元派发 |
| 单条渲染 | `_run_item()` 调用 `render_item()`；渲染器有 FFmpeg 进度、取消、时长校验和 VideoToolbox 回退 | 工作 App 复用渲染器，保存本机尝试记录并上报 |
| 状态 | `data/smartstitch.db` 位于每台 Mac 本机；原有 `_run()` 只在本机线程池并发 | 主控本机数据库保存全批计划与派发状态；工作机数据库保存本机执行状态；通过 API 对账 |
| 共享文件 | 配置和素材在 NAS，输出批次目录也可位于 NAS；计划里含绝对路径 | 下发逻辑 NAS 路径，各工作机转换为本机挂载路径；结果先写唯一暂存文件 |
| 应用生命周期 | 关闭主窗口即退出 App，并取消本机活动任务 | 工作 App 关闭则停止领取、由主控重派；主控在集群运行期间保持打开 |

`ConfigStore` 已能在 `/Volumes/home/Smartstitch` 与 `/Volumes/homes/<用户>/Smartstitch` 之间映射配置路径，但任务快照和选中素材保存的是规划机器的运行时绝对路径。派发协议必须统一路径表示，不能直接把主控的绝对路径交给另一台电脑。

## 推荐结构

```text
Mac A：SmartStitch.app（本批主控，也可渲染）
    本机 SQLite：完整批次计划、派发租约、全批状态
       │ 派发 / 查询 / 取消             ↑ 心跳 / 进度 / 结果
       ├──────── Mac B：SmartStitch.app ── 本机 SQLite：执行记录
       └──────── Mac C：SmartStitch.app ── 本机 SQLite：执行记录

NAS：共享素材、每次尝试的暂存 MP4、最终 MP4、批次快照与清单
```

所有电脑安装同一个 App，不拆成独立前端和后端，也不在 NAS 上安装服务。现有桌面 UI 的本机地址继续绑定 `127.0.0.1`。集群开启时，每台 App 在同一进程内增加一个**仅含集群操作的局域网接口**；不得直接将现有完整管理 API 暴露到局域网。主控可以通过 Bonjour 发现在线 App，也可手动添加节点地址。Bonjour 只用来找地址和端口；真实在线、容量与任务状态要通过认证接口和心跳确认。打包版采用 Bonjour 时，需按 Apple 要求声明局域网用途及服务类型。

### 两层状态的责任

- **主控本机 SQLite 是全批计划与派发的权威**：保存 `batch_id`、不可变条目计划、当前 `attempt_id`、目标工作机、租约期限、最后上报进度、最终接受结果。
- **工作机本机 SQLite 是该机执行事实的权威**：保存收到的派发、FFmpeg 进程状态、进度、错误、暂存文件和完成结果；同一 `(batch_id, item_index, attempt_id)` 重复派发必须幂等。
- 主控周期性调用工作机状态接口对账；工作机也主动上报。工作机断线时，主控依据租约而非一次网络错误判定离线。主控异常崩溃属于故障恢复场景，不作为日常调度路径。

主控数据库中要保留派发记录，不能只依赖工作机数据库；否则工作机关闭时主控无法知道哪些条目需要重新分配。工作机数据库中要保留执行记录，不能只依赖实时回调；否则网络短暂中断后无法补报已完成结果。

### 派发和完成协议

1. 主控一次生成整批计划，决定素材、输出文件名和配置快照。为每条创建唯一条目 ID。
2. 主控从在线 App 中按槽位选择工作机，写入 `attempt_id`、租约和目标节点，再发送派发请求；工作机持久化后应答。请求超时可用相同 `attempt_id` 重发，工作机不能因此启动两次 FFmpeg。
3. 工作机核对版本、FFmpeg 能力、NAS 挂载、素材身份和本机临时空间，运行现有 `render_item()`。按固定间隔更新本机数据库并向主控报告心跳和进度。
4. 工作机在本机完成编码和 ffprobe 校验，将结果复制到 NAS 批次目录中**含 `attempt_id` 的唯一暂存名**，再记录并报告完成。工作机不直接覆盖最终 MP4。
5. 主控只接受当前有效 `attempt_id` 的完成报告，核对暂存文件后发布预先确定的最终文件名。随后把条目标记为完成。数据库写入和 NAS 文件重命名不能组成一个事务，主控重启时必须对账“文件已发布但状态未提交”的情况。
6. 全批终结后，主控唯一写入 `manifest.json`、`manifest.csv` 并触发一次飞书同步。工作机不能各自触发批次级同步。

迟到的旧工作机只能留下自己的暂存文件，不能发布最终文件，也不能覆盖新尝试的状态。暂存文件要有清理规则。取消任务时，主控先停止新派发，再通知在线工作机停止本机 FFmpeg；离线工作机重新出现后也要读取批次取消状态并清理未完成尝试。

### 关闭和故障

| 情况 | 预期行为 |
| --- | --- |
| 工作 App 正常关闭 | 停止本机 FFmpeg，通知主控释放条目；主控不再派给该节点，并把未完成条目派给其他在线节点 |
| 工作 App 崩溃、休眠或断网 | 主控等待心跳与租约超时，再重派；旧尝试恢复后的报告被拒绝 |
| 主控 App 意外退出 | 集群派发暂停，工作机保存执行结果；主控重启后先对账再重派。正常运行时主控保持打开 |
| NAS 不可用 | 不领取依赖该 NAS 的新条目；上传/发布失败保留可诊断状态，恢复后重试 |

这个方案不要求**工作 App** 后台常驻；主控 App 在集群运行期间始终打开。现有 `JobDatabase` 启动时会把本机未结束任务标成 `interrupted`；集群任务仍需独立的异常重启恢复流程，不能沿用这条规则直接结束整批。

## 性能与验收

每台电脑先设 1 个渲染槽位，之后根据 CPU/GPU 使用率、NAS 读写带宽和失败率调整。多机提速不会必然随节点数量线性增长；主素材都从 NAS 读取，最终成片也写回 NAS。建议先用固定配置、种子及 20～50 条成片测单机与双机总耗时，并核对画质和编码器回退情况。

上线前至少在真实两台 Mac 上验证：不同 NAS 挂载路径；工作 App 正常关闭、强制退出、休眠、断网；主控异常重启；派发请求超时重试；旧尝试迟到；NAS 上传中断；最终 MP4 唯一；清单与实际文件一致；飞书同步恰好一次。仓库已实现控制面板、节点局域网接口、派发、状态对账和渲染；本地模拟双机自动化测试通过，但仍缺真实双机及 NAS 故障验收。
