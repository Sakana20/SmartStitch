# 视频超分接入渲染集群设计

状态：首版代码已实现，双机/NAS 实机验收待做。日期：2026-09-23。基于[本机超分方案](25-视频超分接入设计.md)和[现有集群渲染研究](24-多机集群渲染可行性研究.md)。

## 1. 结论和范围

**可接入现有主控 + 工作机体系，但需要新增超分任务协议。** 当前 `ClusterMaster` 派发的是由 `JobManager.create()` 生成的“一条成片计划”，工作机 `ClusterWorker.submit()` 只接受该计划并调用 `render_item()`。超分输入是一段已存在的视频，不具备配置快照、素材选择与成片条目；不能给现有 `job_type="cluster"` 换个名称就直接运行。

对一条视频提速的首选方案是按**连续、互不重叠的帧范围**拆成若干工作块，各工作机用任务指定的同一个模型（`x2plus` 或 `animevideo`）按其原生倍率推理并回缩源视频尺寸，输出无音频的视频片段；主控按帧序拼接视频，仅在最后接回原音频并发布结果。Real-ESRGAN 的逐帧推理没有跨帧状态，因此按帧分工在算法上成立；运动闪烁、切块接缝和编码段边界仍须实测。

每条集群任务使用该条**源视频自己的宽度、高度和有理数帧率**作为所有分段与最终输出的规格；工作机和主控都核对这些值。文中的 1080×1920、24 fps 仅是 H3 样片数据，不是集群输出预设。

首版限定短视频、CFR 输入、macOS arm64 节点；本机模式继续可用。集群批次逐条处理 `原素材` 中的视频，每条视频内部按帧分段分发给空闲工作机。至少一台兼容工作机即可运行，两台及以上才有单条视频的并行收益；跨视频同时派发属于后续优化。

## 2. 最初设计时的能力与缺口

| 项目 | 当前代码实际情况 | 超分需要的改动 |
| --- | --- | --- |
| 控制面 | `cluster.py` 提供私有局域网 `/hello`、`/attempts`、查询和取消；工作机令牌保护可由集群控制页启用；主控发现、节点注册、轮询、重试和唯一暂存名已存在。 | 复用现有认证设置、节点发现与对账框架，增加明确的 `video_upscale` 任务类型和校验；不开放完整本机管理 API 到局域网。 |
| 工作机执行 | `submit()` 验证 NAS 内成片计划和素材，`_run()` 调用 `render_item()`，节点容量固定为 1。 | 增加超分专用执行器；接收共享输入相对路径、精确帧范围、模型/算法版本和编码参数，按帧更新进度并支持取消。 |
| 主控状态 | 成片计划与结果保存在现有 `jobs` 表，工作机尝试存 `cluster_attempts`。 | 新增独立超分作业/分段状态表，或扩展统一表的带版本任务类型；不能把超分结果伪装为成片条目的 `actual_video_encoder` 等字段。 |
| 共享路径 | 当前成片计划只接受 NAS SmartStitch 目录内的素材和输出；主控/工作机通过 canonical root 做挂载别名映射。 | 本地视频先复制到 NAS 私有任务暂存区；仅派发共享根目录下的相对路径。核对真实路径、符号链接、大小和 SHA-256，防止跨目录读写和源文件变化。 |
| 资源状态 | `/hello` 只返回版本、节点名、`active`、固定 `capacity=1` 和 canonical root，没有模型能力字段。 | 增加 CoreML 可用性、架构、模型 ID/ZIP 哈希、算法协议版本、空闲空间、超分槽位、可用/不可用原因。模型不合格的节点不进入调度。 |
| 任务进度 | 主控约 1.5 秒轮询，当前工作机结果字段针对 FFmpeg 成片渲染。 | 分段返回 `processed_frames/total_frames`、阶段、错误、暂存文件信息；主控汇总已完成帧数，另显示源文件准备和最终合并进度。 |

`SQLiteStore.ALLOWED_TABLES` 目前不含超分作业；`cluster_attempts` 只以 `attempt_id` 为主键。实现时应增加明确的 `job_kind`、协议版本和请求摘要，同一 `attempt_id` 重试只有在内容完全相同的情况下才幂等返回，防止不同输入误复用执行记录。

## 3. 用户流程与本地源文件

超分工具面板可选“本机 / 渲染集群”和 `x2plus` / `animevideo`。集群模式固定扫描共享目录 `超分/原素材` 第一层视频，输出到 `超分/已处理`，显示具有**所选模型**的在线节点与待处理列表；无需选择主控本机路径。每条视频固定所选模型及其 ZIP 哈希，所有分段使用同一模型，最终回缩源视频尺寸并输出 MP4。创建前先预检输入、输出和候选工作机。集群控制页仍负责节点上线、令牌和连接；超分工具面板只调用本机受控 API 创建、查询、取消超分作业，不在浏览器中保存工作机令牌。

当前集群入口直接读取 NAS `超分/原素材`，工作机按共享根目录相对路径打开视频，主控核对大小、修改时间和 SHA-256 后派发，不重复复制。旧的单视频集群 API 若接收主控本机文件（例如微信容器路径），仍会先复制到共享暂存区再派发。准备阶段计算帧数、CFR 有理数帧率、显示尺寸、音频信息和工作块边界；启动前检查 NAS 与主控/工作机本地临时空间。

工作机只在本机临时目录保存解码缓存和输出，上传**无音频**分段到 NAS 的含 `attempt_id` 唯一暂存名。主控将按序拼接的最终 MP4 写到 `超分/已处理` 的临时路径，验证后原子改名；输出名包含所选模型且不覆盖已有文件。集群批次保留 `超分/原素材` 中的源文件，已存在同模型目标文件时跳过；任务完成/取消后清理分段暂存，恢复中的暂存不能提前删除。

## 4. 分段、推理与合并协议

1. 主控按 ffprobe 解码核对输入为 CFR、单视频轨、支持的像素格式和显示尺寸。分段使用半开帧区间 `[start_frame, end_frame)`，区间首尾覆盖 `[0, total_frames)`，不重复、不漏帧；默认以约 2–5 秒为一个块，保证可用节点平均至少能领取两块。15.08 秒、24 fps、362 帧的 H3 样片，可先以约 48 帧为一块做 8 个连续块（最后一块 26 帧）验证。
2. 派发 JSON 包含 `kind=video_upscale`、协议版本 2、`job_id`、`attempt_id`、共享输入相对路径和 SHA-256、`start/end` 帧、FPS 分数、输出宽高、所选模型名与资产 SHA-256。工作机必须拒绝未知模型、错误版本或模型不匹配；重试不能重解释工作内容。
3. 工作机从共享源解码指定帧范围，逐帧流式推理、回缩，生成从 PTS 0 开始的**视频轨片段**。首个原型可以顺序解码后丢弃范围外帧以保证帧号正确；若优化为按关键帧预寻址，必须用帧级索引和边界图像验证，不能只用近似秒数 `-ss`。不可用 FFmpeg 的默认按关键帧切段替代精确帧区间。[FFmpeg segment 文档](https://ffmpeg.org/ffmpeg-formats.html#segment_002c-stream_005fsegment_002c-ssegment)说明按时间切段受关键帧约束。
4. 所有工作机使用同一编码器、像素格式、尺寸、帧率、time base、色彩标记和 H.264 参数；每段从可独立解码的关键帧开始，避免开放 GOP 跨段引用。首版可用固定 `libx264` 参数生成无音频 MP4；主控用 FFmpeg concat demuxer 按序无损拼接视频轨，再从源文件接回音频（封装兼容时复制，否则转 AAC）。[FFmpeg concat 文档](https://ffmpeg.org/ffmpeg-formats.html#concat)要求各输入具有一致的流结构与参数。拼接失败必须报错，不静默降质重编码。
5. 主控检查每段的帧数等于 `end-start`，视频流参数和哈希符合预期，再接受当前有效 `attempt_id`。最终核对帧数、尺寸、FPS、时长、首尾帧、音轨与 A/V 同步；只在全部通过后发布。视频段不可包含音频，避免边界处音频重复或断裂。

具体解码与拼接命令须在 1 秒、2 秒和非整秒末尾样片上原型验证后固定。完整连续视频验收前，不能将“可按帧拆分”当成已验证的无缝合并能力。

## 5. 调度、能力与性能预期

- 节点预检需在工作机本机校验所选模型：输入 `[1,3,522,522]`，`x2plus` 输出 `[1,3,1044,1044]`，`animevideo` 输出 `[1,3,2088,2088]`。不能仅凭 App 版本判断具备超分能力。各机安装同版 App/模型，不能在接任务后隐式下载。`coremltools`/CoreML 首次编译可能较慢。
- 每台机器默认只有一个重型视频执行槽位，普通成片渲染与超分共享该资源门禁，避免同机一边 FFmpeg 渲染、一边 CoreML 超分导致内存或 GPU 争用。当前 `ClusterWorker.status()` 只有一个 `capacity=1`，扩展时要让本机超分工具任务也参与占用统计。
- `ALL` 在本次 16 GB M4 Mac mini 单帧测试约 0.18–0.19 秒/512 块，整帧 12 块推理 2.23 秒；15 秒、362 帧仅推理粗估 13–14 分钟。两台同级空闲节点的理想推理下限约 7 分钟，四台约 3–4 分钟，**均未计**模型加载、源文件复制、重复解码、NAS 传输、编码、合并和节点差异。不能把节点数直接当作实际提速倍数。
- 主控根据工作机完成速度继续分派剩余块，避免慢节点拖累整片；首版可先按空闲槽位调度。在线节点为 0、模型版本不匹配或 NAS 不可用时暂停派发并显示原因；不要把耗时超分任务自动派给不兼容节点。若总任务过短，分段与 NAS 开销可能抵消并行收益，界面应建议本机模式。

## 6. 状态恢复、取消与安全边界

主控本机 SQLite 保存作业、源文件指纹、每段边界、当前 `attempt_id`、目标节点、租约、最终输出路径和发布阶段；工作机本机 SQLite 保存每次尝试的不可变请求摘要、进度、错误与 NAS 暂存文件。工作机崩溃或失联后，主控按租约而非单次 HTTP 超时重派未完成段。旧工作机迟到时只能留下自己的唯一暂存文件，不能覆盖主控已接受的新尝试；主控重启先对账已完成分段和可能已发布的最终文件，再继续。

取消先停止新派发，再通知工作机中断解码/CoreML 帧循环/FFmpeg 编码并清理本机临时文件。CoreML 单次 `predict()` 不一定能即时中断，至少每 tile 或每帧检查取消标记；离线节点恢复后应读取取消状态，放弃迟到结果。主控 App 退出提示要统计超分作业；工作机退出按现有集群机制停止本机执行。源文件复制、分段上传和最终复制都必须写唯一临时名，禁止覆写已有输出。

局域网接口沿用工作机的可选令牌保护设置，不暴露任意文件读取接口。工作机只接受共享根目录 `超分/原素材` 内的输入，或 `.video-upscale/<作业 ID>/source.mp4` 暂存输入；分段输出仅写入该作业的暂存目录，解析符号链接后再校验。请求中的模型路径、FFmpeg 命令及输出绝对路径都不能由主控任意指定。现有局域网链路是受信任私网 HTTP，部署条件延续[集群文档](24-多机集群渲染可行性研究.md)；通过 NAS 共享视频与分段属于用户可见的数据复制，不上传到模型服务。

## 7. 实现顺序与验收

1. **先完成本机视频闭环**：1–2 秒样片逐帧超分、原尺寸输出、音频保留、取消和资源界限。当前仅完成单帧模型测试；这一步不能跳过。
2. **再验证分段原型**：同一台机器分别以“不分段”和“分为 2/8 段”处理同一短视频，核对全部 362 帧、边界前后图像、PTS 单调、长度与音频同步。若编码参数无法稳定无损拼接，先解决协议，不能带着不确定性进入集群。
3. 增加独立超分作业/尝试存储、能力握手、typed 派发、共享输入暂存、资源槽位和主控合并；扩展超分面板选择执行位置、查看节点和取消。普通集群成片任务保持现有协议和记录语义。
4. 用两台真实 Apple Silicon Mac 和 NAS 验证不同挂载别名、不同芯片与内存、模型缺失/哈希错误、源文件变化、节点休眠/断网/退出、主控重启、取消、重复派发、迟到结果、NAS 空间不足及本地输出发布。记录单机与双机端到端耗时、峰值内存、NAS 读写量和画质差异；只有端到端收益明确后才默认推荐集群模式。

## 8. 已落地的首版

- `video_upscale.py` 提供 `x2plus` / `animevideo` 模型校验、逐帧处理、无声片段生成和最终音频回接。App 构建流程校验并内置两款模型，工作机安装同一 App 后可离线加载；当前仍需正式包验证。`cluster.py` 的工作机新增 `/upscale-attempts`，沿用该工作机当前的可选令牌保护设置，校验协议版本、所选模型与 SHA、NAS 相对路径、源文件 SHA、帧范围与同 ID 请求摘要；普通成片协议仍独立。
- `cluster_upscale.py` 的集群入口扫描 NAS `超分/原素材` 第一层，跳过 `超分/已处理` 中已有同模型结果的文件；每条视频按 48 帧派发半开区间。NAS 输入以共享相对路径直接供工作机读取，不再重复复制；旧单视频 API 的本机输入仍可暂存到 `.video-upscale/<作业 ID>/`。工作机上传按 attempt ID 命名的无声 MP4；主控核对哈希及帧数后 concat、接回音频，原子发布到 `已处理`。单视频和批次分别保存在 SQLite `upscale_jobs` / `upscale_batches`，可取消并尝试在主控重启后恢复。工作机使用同一内置模型版本，无需逐台下载。
- 自动化测试用一台模拟工作机完成 NAS 外源文件暂存、派发、拼接、音频回接和尺寸/帧数校验，并验证同一个 attempt ID 的不同请求被拒绝。真实 H3 视频 `[0,2)` 与 `[2,4)` 两段也已用 CoreML 实际推理并成功拼接成 4 帧有声 MP4。
- **尚未实测**两台真实 Mac 和 NAS、网络断连后的恢复、完整 362 帧性能与运动画质、正式 App/DMG 中的 CoreML 运行。当前未按节点实测内存/磁盘容量进行准入，未做源视频字节级复制进度或最终音频同步误差的自动测量。这些是发布前验收项，不应把上述最小化测试解释为生产验收完成。
